## 1. Learning outcomes: report figure vs dashboard view

After this lesson, you should be able to:

-   Build a self-contained figure whose title, scope, units, source, freshness, sample size, and caveats travel with it.
-   Select PNG, SVG, PDF, or interactive HTML based on audience, rendering needs, privacy, and file size.
-   Apply a reusable style and figure factory to produce consistent report graphics.
-   Create a small, coherent Pipeline Health report with KPIs, trends, SLO thresholds, a failure breakdown, and a lightweight dashboard prototype.
-   Define metrics precisely, reconcile displayed numbers against the source of truth, and disclose uncertainty and limitations.
-   Generate reports from versioned data, test data quality, add visual regression checks, and publish only reviewed artifacts.
-   Evaluate accessibility, privacy, performance, and visual quality without overbuilding the dashboard.

### Report figure and dashboard view are related but different

  Concern           Report figure                                             Dashboard view
  ----------------- --------------------------------------------------------- --------------------------------------------------------------------------------
  Primary job       Explain a finding and support a decision                  Monitor state and guide the next investigation
  Time              Usually a defined snapshot/window                         Often a selected or changing window
  Context           Caption, source, method, caveats travel with the figure   Filters, freshness, definitions, and source links remain visible in the view
  Interaction       Usually static; annotation carries the story              Filters and drill-down may change the displayed slice
  Reproducibility   Regenerate from code and versioned inputs                 Same metric definitions and data version must be used for each selected state
  Main risk         A misleading or decontextualized export                   A polished interface that hides stale data, definitions, or empty/error states

A dashboard is not automatically trustworthy because it looks polished. Every displayed number needs a definition, a source, a time window, and a reconciliation path to the source of truth.

## 2. Principles of a self-contained, trustworthy figure

A useful figure answers one clear question and supports one decision. Put enough context in the figure or its caption that it remains interpretable when copied into a report or slide.

### Figure anatomy

1.  **Takeaway title:** state the main observation, not merely "Pipeline duration."
2.  **Subtitle/scope:** define the time window, filters, environment, and whether data are provisional.
3.  **Axes and units:** use precise names and units; label transformed scales.
4.  **Legend/direct labels:** explain series, category ordering, and line meaning. Prefer direct labels when they reduce legend lookup.
5.  **Source and version:** identify the data source, immutable snapshot/version, and generation script or notebook.
6.  **Freshness:** state when data were last updated, with timezone.
7.  **Sample size/denominator:** show counts behind rates and aggregates; distinguish missing observations from zero.
8.  **Caveats/uncertainty:** describe missing periods, late-arriving data, sampling, confidence intervals, or known measurement limits.
9.  **Accessible alternatives:** provide alt text and, where useful, a small data table or textual summary.
10. **Provenance:** include report/run ID or build revision when readers may need to reproduce the figure.

Example caption:

> **Figure 1.** Synthetic pipeline success rate remained above the 95% target in the selected 7-day window. Success rate = successful runs / all completed runs; n = 168 runs. Source: synthetic `pipeline_runs` fixture v1; generated by `reports/build_report.py`, run ID `demo-001`. Values are illustrative and do not represent a real service. Late-arriving runs are excluded from this fixed snapshot.

The title should not imply causation from a mere association. If the chart shows a change but does not establish why it occurred, say "increased after" or "coincided with," not "caused by."

### Choose tables or charts deliberately

-   Use a **table** for exact lookup, detailed values, or comparisons that require precise reading.
-   Use a **chart** for pattern, distribution, trend, ranking, or relationship.
-   Use both only when they serve distinct needs. Do not make readers decode a chart to recover a value that should be a table cell.
-   Format numbers with explicit units, separators, and appropriate rounding. A 0.5 percentage-point change is not the same as a 0.5% relative change.

## 3. Export format and size trade-offs

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Format                                  Best use                                                  Strengths                                       Trade-offs and checks
  --------------------------------------- --------------------------------------------------------- ----------------------------------------------- ----------------------------------------------------------------------------------------------------------
  PNG                                     Documents, chat, slides, previews                         Broad support; predictable raster output        Resolution depends on pixel dimensions/DPI; text can blur when enlarged

  SVG                                     Web pages, vector editing, scalable diagrams              Crisp at many sizes; text/paths remain vector   Some renderers differ; embedded fonts/images and external references need review

  PDF                                     Papers, print, multi-figure reports                       Vector graphics; convenient for print           Fonts, transparency, and viewer behavior must be checked; may need layout tooling

  Interactive HTML                        Lightweight exploration and self-contained web reports    Hover, zoom, filters, selectable series         May embed the plotted data; can be large; interactive controls do not guarantee accessibility or privacy

  CSV/JSON companion                      Exact values, downstream checks, accessible alternative   Machine-readable, auditable values              Does not replace a visual summary; define schema, units, and version
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### Dimensions, DPI, and fonts

-   Choose `figsize` for the **final physical size** (inches) of the report column, page, or slide---not just what looks good in a notebook.
-   For raster output, 150--300 DPI is a common starting point for reports/print. Pixel dimensions are approximately inches × DPI. A 7 × 4 inch figure at 200 DPI is about 1400 × 800 pixels.
-   SVG/PDF are vector formats for most Matplotlib line/text elements, but rasterized artists and embedded images remain raster.
-   Set `bbox_inches="tight"` when appropriate, but inspect the result: tight bounding boxes can clip or reposition elements unexpectedly in some downstream layouts.
-   Embed fonts where supported by the export path; inspect the final PDF/SVG in the target renderer. Use consistent font families and sizes; aim for roughly 8--10 pt or larger at final print size.
-   Transparent backgrounds can blend poorly into dark/light report themes. Test the figure against its actual destination.
-   Interactive HTML file size grows with traces, points, hover fields, and bundled JavaScript. Aggregate or downsample first; inspect the output before sharing.

## 4. Basic: report-ready figures and a lightweight dashboard

### Consistent layout and typography

Use a hierarchy: one clear title, a concise scope line, the visual, then source/caveat text. Align axes in small multiples; use whitespace to separate concepts; limit the palette; minimize unnecessary gridlines and chart junk. Keep legend order, category colors, units, and date formats consistent across figures.

A "house style" is a small documented set of decisions: palette, fonts, grid/spine behavior, title placement, numeric formatting, and meaning assigned to colors. Do not use red/green alone to encode status; add labels or shapes.

### A small synthetic Pipeline Health case study

We will use a deterministic, synthetic dataset. The numbers in this lesson are examples for teaching---not production findings.

Each row in `pipeline_runs.csv` represents one pipeline execution. Expected fields:

  Field                      Type / unit          Meaning
  -------------------------- -------------------- ------------------------------------------------------------------------
  `run_id`                   string               Synthetic unique run identifier; not a customer identifier
  `started_at`               ISO timestamp, UTC   Start time
  `status`                   category             `success`, `failed`, or `cancelled`
  `duration_seconds`         seconds              Elapsed run time, positive numeric value
  `data_freshness_minutes`   minutes              Delay between latest expected data event and data available to the job
  `rows_processed`           rows                 Rows processed in that run
  `failure_reason`           category or null     Controlled failure category; null for successful runs

**Metric dictionary**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Metric                          Definition                                                                                                                         Unit / aggregation                                   Owner / source                                  Freshness and caveats
  ------------------------------- ---------------------------------------------------------------------------------------------------------------------------------- ---------------------------------------------------- ----------------------------------------------- ---------------------------------------------------------------
  Success rate                    successful runs / completed runs × 100; completed means `success` or `failed`, excluding `cancelled`                               percent; aggregate numerator and denominator first   Data Platform / versioned `pipeline_runs.csv`   7-day window; report `n`; cancelled runs are shown separately

  p95 duration                    95th percentile of `duration_seconds` for completed runs                                                                           seconds; percentile over run-level observations      Data Platform / same snapshot                   Sensitive to workload mix; not the mean

  Data freshness                  Median `data_freshness_minutes` for completed runs                                                                                 minutes; median                                      Data Platform / same snapshot                   Lower is fresher; null values reduce metric sample size

  Row-count anomaly               Run-level rows processed outside a declared baseline band, e.g. less than 80% or greater than 120% of a versioned expected count   count and percent of completed runs                  Data Quality / versioned baseline               Illustrative baseline only; volume shifts may be legitimate

  Failure breakdown               Failed runs grouped by controlled `failure_reason`                                                                                 count; denominator is all failed runs in window      Data Platform / same snapshot                   Small categories may require suppression before publication
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

For the teaching example, set the success target to 95%, duration SLO to 300 seconds at p95, freshness SLO to 60 minutes median, and row-count baseline to 1,000 rows with a 20% tolerance. These are **illustrative thresholds**, not universal recommendations. A real owner must approve definitions and targets.

### Create a deterministic synthetic dataset

Save as `reports/make_sample_data.py`:

``` python
from pathlib import Path

import pandas as pd

def make_sample_runs() -> pd.DataFrame:
    """Return deterministic synthetic pipeline runs for tests and examples."""
    rows = []
    reasons = ["source_timeout", "schema_change", "resource_limit"]
    for day in range(7):
        for slot in range(24):
            index = day * 24 + slot
            status = "failed" if index % 13 == 0 else (
                "cancelled" if index % 17 == 0 else "success"
            )
            duration = 80 + (index * 19) % 360
            freshness = 15 + (index * 7) % 95
            row_count = 1000 + ((index % 9) - 4) * 55
            reason = reasons[index % len(reasons)] if status == "failed" else None
            rows.append({
                "run_id": f"demo-{index:04d}",
                "started_at": pd.Timestamp("2026-10-12T00:00:00Z")
                    + pd.Timedelta(hours=index),
                "status": status,
                "duration_seconds": float(duration),
                "data_freshness_minutes": float(freshness),
                "rows_processed": int(row_count),
                "failure_reason": reason,
            })
    return pd.DataFrame(rows)

if __name__ == "__main__":
    destination = Path("data/synthetic/pipeline_runs.csv")
    destination.parent.mkdir(parents=True, exist_ok=True)
    make_sample_runs().to_csv(destination, index=False)
    print(f"Wrote synthetic fixture: {destination}")
```

### Figure 1 --- success rate over time

**Question answered:** Did the share of completed runs meeting the success outcome remain above the target during the selected window?\
**Decision supported:** Investigate periods below the target; do not infer a cause from this chart alone.

``` python
from pathlib import Path

import matplotlib.pyplot as plt
import pandas as pd

def completed_runs(frame: pd.DataFrame) -> pd.DataFrame:
    return frame.loc[frame["status"].isin(["success", "failed"])].copy()

def plot_success_rate(frame: pd.DataFrame, output: Path) -> None:
    completed = completed_runs(frame)
    window_start = pd.to_datetime(frame["started_at"], utc=True).min().date()
    window_end = pd.to_datetime(frame["started_at"], utc=True).max().date()
    completed["day"] = pd.to_datetime(completed["started_at"], utc=True).dt.date
    daily = completed.groupby("day").agg(
        completed=("run_id", "size"),
        successful=("status", lambda values: int((values == "success").sum())),
    )
    daily["success_rate_pct"] = 100 * daily["successful"] / daily["completed"]

    fig, ax = plt.subplots(figsize=(7, 3.8), layout="constrained")
    ax.plot(daily.index.astype(str), daily["success_rate_pct"], marker="o",
            label="Daily success rate")
    for x, (_, row) in enumerate(daily.iterrows()):
        ax.annotate(f"n={int(row['completed'])}", (x, row["success_rate_pct"]),
                    xytext=(0, 7), textcoords="offset points", ha="center", fontsize=7)
    ax.axhline(95, linestyle="--", linewidth=1.5, label="Illustrative target: 95%")
    minimum = daily["success_rate_pct"].min()
    maximum = daily["success_rate_pct"].max()
    ax.set(title=f"Daily success rate ranged from {minimum:.1f}% to {maximum:.1f}%",
           xlabel="Start date (UTC)", ylabel="Completed runs successful (%)")
    ax.set_ylim(0, 105)
    ax.tick_params(axis="x", rotation=30)
    ax.legend(frameon=False)
    fig.text(0.01, -0.02,
             f"Source: data/synthetic/pipeline_runs.csv · synthetic-v1 · {window_start} to {window_end} UTC · "
             f"n={len(completed)} completed runs; cancelled runs excluded; "
             "generated by reports/pipeline_health.py.",
             fontsize=8)
    output.parent.mkdir(parents=True, exist_ok=True)
    fig.savefig(output, dpi=200, bbox_inches="tight")
    plt.close(fig)
```

### Figure 2 --- duration and SLO threshold

**Question answered:** Is the upper tail of completed-run duration within the illustrative p95 target?\
**Decision supported:** Inspect slow-run diagnostics when p95 exceeds 300 seconds; do not replace the percentile with an average.

``` python
def plot_duration(frame: pd.DataFrame, output: Path) -> None:
    completed = completed_runs(frame)
    window_start = pd.to_datetime(frame["started_at"], utc=True).min().date()
```

### Figure 3 --- failure breakdown

**Question answered:** Which controlled failure categories account for the failed runs in this sample?\
**Decision supported:** Prioritize investigation by count, while checking whether categories differ in severity or cost.

``` python
def plot_failures(frame: pd.DataFrame, output: Path) -> None:
    window_start = pd.to_datetime(frame["started_at"], utc=True).min().date()
    window_end = pd.to_datetime(frame["started_at"], utc=True).max().date()
    failures = frame.loc[frame["status"].eq("failed")]
    counts = failures["failure_reason"].fillna("Unclassified").value_counts().sort_values()
    if counts.empty:
        counts = pd.Series({"No failures in window": 0}, dtype="int64")

    fig, ax = plt.subplots(figsize=(7, 3.8), layout="constrained")
    counts.plot.barh(ax=ax)
    top_reason = counts.idxmax()
    top_count = int(counts.max())
    ax.set(title=f"Most frequent failure category: {top_reason} ({top_count} runs)",
           xlabel="Failed runs (count)", ylabel="Controlled failure category")
    for container in ax.containers:
        ax.bar_label(container, fmt="%d", padding=3)
    fig.text(0.01, -0.02,
             f"Source: data/synthetic/pipeline_runs.csv · synthetic-v1 · {window_start} to {window_end} UTC · n={len(failures)} failed runs; "
             "denominator is all failed runs; generated by reports/pipeline_health.py.",
             fontsize=8)
    output.parent.mkdir(parents=True, exist_ok=True)
    fig.savefig(output, dpi=200, bbox_inches="tight")
    plt.close(fig)
```

### Figure 4 --- daily p95 duration trend

The histogram answers a distribution question; a time-series view answers whether the tail changed by day. Use the same UTC day boundaries as the success-rate chart and retain missing days as gaps rather than zeroes.

```python
def plot_daily_p95_duration(frame: pd.DataFrame, output: Path) -> None:
    completed = completed_runs(frame).copy()
    window_start = pd.to_datetime(frame["started_at"], utc=True).min().date()
    window_end = pd.to_datetime(frame["started_at"], utc=True).max().date()
    completed["day"] = pd.to_datetime(completed["started_at"], utc=True).dt.floor("D")
    daily = completed.groupby("day").agg(
        p95_seconds=("duration_seconds", lambda values: values.dropna().quantile(.95)),
        n=("duration_seconds", "count"),
    )
    if daily["p95_seconds"].notna().sum() == 0:
        raise ValueError("No non-null duration values available for daily p95")
    fig, ax = plt.subplots(figsize=(7, 3.8), layout="constrained")
    ax.plot(daily.index, daily["p95_seconds"], marker="o", label="Daily p95 duration")
    ax.axhline(300, linestyle=":", linewidth=2, label="Illustrative p95 target: 300 s")
    for x, (_, row) in enumerate(daily.iterrows()):
        if pd.notna(row["p95_seconds"]):
            ax.annotate(f"n={int(row['n'])}", (daily.index[x], row["p95_seconds"]),
                        xytext=(0, 7), textcoords="offset points", ha="center", fontsize=7)
    ax.set(title="Daily p95 duration compared with the 300 s target",
           xlabel="Start date (UTC)", ylabel="p95 duration (seconds)")
    ax.legend(frameon=False)
    fig.text(0.01, -0.02,
             f"Source: data/synthetic/pipeline_runs.csv · synthetic-v1 · {window_start} to {window_end} UTC · "
             f"n={int(daily['n'].sum())} non-null completed-run durations; "
             "generated by reports/pipeline_health.py.", fontsize=8)
    output.parent.mkdir(parents=True, exist_ok=True)
    fig.savefig(output, dpi=200, bbox_inches="tight")
    plt.close(fig)
```

The examples show source, data version, sample size and generation path in the figure footnotes. The report page records build time and the metric/data versions. In production, add an immutable run ID and the Git revision to the report manifest. Keep the same category-color mapping across charts and views.

### Lightweight dashboard layout

A compact dashboard should follow this order:

1.  **KPI row:** success rate with numerator/denominator, p95 duration in seconds, median freshness in minutes, row-count anomaly count.
2.  **Trends:** daily success rate and duration trend with visible SLO/target lines.
3.  **Breakdown:** failure reasons, sorted by count and with the denominator stated.
4.  **Diagnostic detail:** only a safe, paginated summary of aggregate or de-identified records; link to a restricted source/runbook rather than embedding raw rows.
5.  **Controls:** a clearly labelled UTC date range and optional environment filter; display the effective filter and last-updated timestamp.
6.  **State handling:** explicit loading, empty, stale, and error states. A missing day must not silently become zero success.

Keep the first view to roughly 6--8 visuals or fewer. Do not build a full BI platform for this lesson. A lightweight Streamlit-style prototype can use the same metric functions and pre-aggregated table; the next section gives a minimal example.

### Validate inputs and define metrics once

```python
from pathlib import Path
import json

import pandas as pd

REQUIRED_COLUMNS = {
    "run_id", "started_at", "status", "duration_seconds",
    "data_freshness_minutes", "rows_processed", "failure_reason",
}


def load_runs(path: Path) -> pd.DataFrame:
    frame = pd.read_csv(path, parse_dates=["started_at"])
    missing = REQUIRED_COLUMNS - set(frame.columns)
    if missing:
        raise ValueError(f"Missing required columns: {sorted(missing)}")
    if frame["run_id"].isna().any() or frame["run_id"].duplicated().any():
        raise ValueError("run_id must be present and unique")
    if not frame["status"].isin(["success", "failed", "cancelled"]).all():
        raise ValueError("Unexpected status value")
    if (frame["duration_seconds"].dropna() < 0).any():
        raise ValueError("duration_seconds cannot be negative")
    # Parse explicitly as UTC; naive source timestamps are interpreted as UTC here
    # only because the synthetic fixture contract says timestamps are UTC.
    frame["started_at"] = pd.to_datetime(frame["started_at"], utc=True, errors="raise")
    return frame.sort_values(["started_at", "run_id"]).reset_index(drop=True)


def calculate_metrics(frame: pd.DataFrame) -> dict:
    completed = completed_runs(frame)
    if completed.empty:
        raise ValueError("No completed runs in the selected snapshot")
    failures = frame.loc[frame["status"].eq("failed")]
    row_count_outside = ~completed["rows_processed"].between(800, 1200, inclusive="both")
    return {
        "metric_version": "pipeline-health-v1",
        "window_start_utc": frame["started_at"].min().isoformat(),
        "window_end_utc": frame["started_at"].max().isoformat(),
        "total_runs": int(len(frame)),
        "cancelled_runs": int(frame["status"].eq("cancelled").sum()),
        "completed_runs": int(len(completed)),
        "successful_runs": int(completed["status"].eq("success").sum()),
        "success_rate_pct": float(100 * completed["status"].eq("success").mean()),
        "p95_duration_seconds": float(completed["duration_seconds"].dropna().quantile(.95)),
        "duration_n": int(completed["duration_seconds"].notna().sum()),
        "median_freshness_minutes": float(completed["data_freshness_minutes"].dropna().median()),
        "freshness_n": int(completed["data_freshness_minutes"].notna().sum()),
        "row_count_anomaly_runs": int(row_count_outside.sum()),
        "row_count_anomaly_pct": float(100 * row_count_outside.mean()),
        "failed_runs": int(len(failures)),
        "failure_reason_counts": {
            str(key): int(value)
            for key, value in failures["failure_reason"].fillna("Unclassified").value_counts().sort_index().items()
        },
        "source": "data/synthetic/pipeline_runs.csv",
        "data_version": "synthetic-v1",
        "synthetic": True,
    }
```

**Interpretation constraints:** the success rate denominator is completed runs (`success` + `failed`), not all started runs; cancellations are reported separately. Row-count anomalies use the illustrative inclusive range 800–1,200 for every run, and this is not a production anomaly detector. If a real pipeline has workload-specific baselines, compare against a versioned baseline by pipeline and run type. Null duration/freshness values are excluded from their respective statistics and their sample counts are exposed. An empty or all-null metric should fail the build or render an explicit “no data” state, not silently become zero.

### Build the figures, metrics JSON, and HTML report

Add this final orchestration to `reports/pipeline_health.py` after the plotting functions above. It deliberately uses a fixed output directory for this teaching build; production automation should add a run ID and write to a fresh directory to avoid overwriting artifacts from another run.

```python
    return output_dir / "index.html"


if __name__ == "__main__":
    print(f"Built report: {build_report()}")
```

The HTML report is a static report, not a live dashboard. It contains only generated aggregate figures and a link-by-convention to the neighboring metrics file; it does not embed raw run records. Review the exact HTML and images before publishing. Do not publish `metrics.json` or source data if they include sensitive operational detail in a real system.

## 6. Dashboard implementation choices and performance

Choose a lightweight tool by the audience and operating constraints, not by fashion:

| Option | Good fit | Trade-off to check |
|---|---|---|
| Streamlit | Internal Python-first prototype with limited interaction | App reruns and state management need care; protect every data access path |
| Plotly Dash | Custom interactive views and callbacks | More explicit callback architecture and deployment work |
| Panel | Python visualization ecosystem and linked views | Team familiarity and packaging matter |
| Grafana | Operational time-series metrics and alerting | Not a substitute for a carefully defined analytical report |
| Superset/Metabase/Looker | Governed BI over shared data models | Serving, permissions and semantic definitions are broader platform concerns and out of scope here |
| Static HTML/PDF | Scheduled snapshot for broad readership | No live filtering; regenerate for a new data snapshot |

Before choosing, document the audience, data volume, refresh interval, authentication/SSO needs, authorization model, and acceptable query cost. For operational or customer data, enforce authorization on the server/data layer; hiding a UI control is not access control.

Performance patterns for a larger dataset:

- Aggregate in SQL/DuckDB or a materialized table before data reaches the browser. Avoid shipping raw rows when aggregates answer the question.
- Use WebGL-aware traces for dense scatterplots only after measuring browser/device support and visual trade-offs.
- For dense time series, consider LTTB or another documented downsampling algorithm; preserve extrema/events where operationally important and disclose that the display is sampled.
- Lazy-load detail panels, paginate tables, and cache expensive aggregations/callbacks with explicit invalidation keys (data version, filters, permissions, metric version). Never share cached results across users with different authorization scopes.
- Show loading, stale, empty, and error states; record query duration and page-load time. Do not convert timeouts or missing data into zero values.

## 7. Reusable style, report assembly, and automated quality gates

Put house-style choices in one version-controlled place. For Matplotlib, a project `.mplstyle` file or a small `plotkit` module can define fonts, palette, grid and spine rules. For Plotly, define a named `plotly.io.templates` template. Document semantic colors (for example, red means failed/error, blue means baseline) and provide a dark-background variant with contrast checks. Never rely on color alone: combine color with text, shape, line style, or marker.

Use reusable figure factories for common patterns (time series with target line, before/after panels, sorted failure breakdown, small multiples). Pass metric data and definitions explicitly; avoid global mutable plotting state. For small multiples, share axes only when the scales and units are comparable. If scales differ, label that choice prominently rather than suggesting direct visual comparability.

A report build should be one documented command, for example `make report`, `uv run python -m reports.build`, or a Quarto render command. Keep source data/version, analysis code, figures, report and metrics dictionary connected in the build. Report formats can include Markdown, Quarto, Jupyter Book/Sphinx, LaTeX/PDF, `nbconvert` HTML, `reveal.js`, or PowerPoint via `python-pptx`; choose one appropriate to the audience rather than combining every format.

A minimal illustrative Make target (adapt paths to your repository):

```makefile
.PHONY: report test
report:
	uv run python reports/make_sample_data.py
	uv run python -m reports.pipeline_health

test:
	uv run pytest -q
```

For production data, the build should consume a versioned snapshot rather than regenerate a synthetic fixture. Preserve run IDs or build revisions; use a fresh output directory or atomic temporary files followed by rename; never silently overwrite another run's outputs. A retry is safe only if its writes are idempotent or duplicate side effects are prevented.

### Metric dictionary (one-page starting point)

| Metric | Definition and denominator | Unit / aggregation | Owner / source / version | Freshness and caveat |
|---|---|---|---|---|
| Success rate | Successful completed runs / completed runs (`success` + `failed`) | Percent; aggregate counts before division | Data Platform; versioned run-log snapshot | Cancelled runs excluded; show numerator, denominator and window |
| p95 duration | 95th percentile of non-null duration among completed runs | Seconds; run-level percentile | Data Platform; same snapshot | Not an average; workload mix affects comparisons; display `n` |
| Median freshness | Median non-null freshness among completed runs | Minutes | Data Platform; same snapshot | Lower is fresher; expose sample count and missingness |
| Row-count anomaly | Completed runs with rows outside versioned expected band | Count and percent of completed runs | Data Quality; baseline version | Example band 800–1,200 is synthetic only; volume shifts may be legitimate |
| Failure breakdown | Failed runs grouped by controlled failure category | Count; denominator = all failed runs | Data Platform; same snapshot | Sort deterministically; suppress or combine small cells before sharing |

Keep the dictionary alongside the report and change it when definitions change. A dashboard must use the same metric functions or governed query as the report; independently reimplementing formulas in UI callbacks invites mismatches.

## 8. Visual QA, accessibility, privacy, and ethics checklist

Before approving an artifact, check every item that applies:

- [ ] Spot-check at least one displayed number against raw/source-of-truth rows and the metric dictionary; reconcile numerator, denominator and window.
- [ ] Verify axis starts, limits, units, log transforms, target lines, legend order, category order and consistent color semantics.
- [ ] Check title/takeaway, subtitle filters/dates/sample size, source and data version, last-updated time with timezone, and material caveats.
- [ ] Inspect text at final print/slide/mobile size; avoid overlapping labels; test SVG/PDF and raster exports in the destination renderer.
- [ ] Check rounding and distinguish percentages from percentage-point changes; avoid false precision beyond the data quality.
- [ ] Verify missing time periods remain missing or explicitly marked; distinguish no events from unavailable data.
- [ ] Test empty, stale, loading and error states; inspect mobile, print, dark mode and keyboard navigation for interactive views.
- [ ] Provide alt text and a textual/data-table alternative where useful; ensure contrast and never encode status using color alone.
- [ ] Inspect interactive HTML for embedded data, hover fields, source URLs, identifiers, hidden traces and CDN/offline behavior. A static image may still disclose a sensitive label; HTML may expose far more.
- [ ] Apply server-side authorization, PII masking, audit logs and small-cell suppression where relevant. A k-anonymity threshold is a policy aid, not a guarantee against re-identification.
- [ ] Disclose provisional data, late-arriving/restated values, sampling, uncertainty, methodology links and model limitations. Group comparisons need context and denominators; do not imply groups are inherently deficient from a metric gap.
- [ ] Retain the approved artifact, build/run ID and source revision according to policy; publish only reviewed files to an access-controlled destination.

For AI-system reporting at this lesson's preview level, a small gallery may include quality evaluation with confidence intervals, regression gates, cost/latency/token use by model and route, retrieval metrics, guardrail triggers, drift indicators, and human-feedback rates. Show sample sizes and evaluation-set/version, avoid implying one metric fully represents model quality, and sample prompts/outputs only under an explicit privacy policy. Do not turn this lesson into a full ML-evaluation or dashboard-platform course.

## 9. Golden-image tests and automated builds

Golden-image tests catch unintended rendering changes, but pixels can vary with fonts, OS, Matplotlib versions and rendering backends. Pin the environment and use a documented tolerance; inspect diffs instead of automatically accepting every new baseline. Keep a data/metric correctness test separate from a visual comparison.

A small test for metric semantics and the deterministic fixture can be written as follows, assuming the functions are in `reports/pipeline_health.py`:

```python
from reports.make_sample_data import make_sample_runs
from reports.pipeline_health import calculate_metrics


def test_success_rate_denominator_excludes_cancelled_runs():
    frame = make_sample_runs()
    metrics = calculate_metrics(frame)
    completed = frame[frame["status"].isin(["success", "failed"])]
    expected = 100 * (completed["status"] == "success").sum() / len(completed)
    assert metrics["completed_runs"] == len(completed)
    assert metrics["success_rate_pct"] == expected


def test_fixture_is_deterministic():
    first = make_sample_runs()
    second = make_sample_runs()
    assert first.equals(second)
```

For image regression, use a tool such as `pytest-mpl` with a pinned rendering environment, and set a tolerance based on expected platform variability. A test should fail if the metric definition changes unexpectedly; a golden image alone cannot prove the number is correct. CI should build on merge, run data-quality/unit/visual tests, retain HTML/PNG/SVG/metrics artifacts, and make warnings policy explicit. The CI provider's YAML is provider-specific; keep the general contract independent of GitHub Actions, GitLab CI, or another runner.

## 10. Common mistakes

- Dashboard with many unrelated charts and no information hierarchy.
- Figure title says only the metric name, with no finding or scope.
- A rate is shown without numerator, denominator or time window.
- Percent and percentage-point changes are conflated.
- p95 is described as an average, or missing data are silently plotted as zero.
- The same metric is calculated differently in the report and dashboard.
- The color palette changes meaning between pages, or red/green is the only status cue.
- Interactive HTML exposes row-level data or sensitive hover fields.
- Visual regression snapshots are updated without reviewing the cause.
- Figures are manually edited after export and cannot be regenerated.
- A synthetic threshold is presented as a production SLO.
- A dashboard is published without authentication, authorization, freshness, empty-state or error-state checks.

## 11. Self-check

1. **What makes a figure self-contained for a report reader?** Include a takeaway title, scope/date/filter subtitle, labeled axes and units, source and data version, freshness/timezone, sample size/denominator, caveats/uncertainty, and accessible text/data alternative where useful.
2. **How do you make sure a dashboard number matches the source of truth?** Define it in a metric dictionary, use a versioned source snapshot and shared metric/query implementation, state the time window and filters, expose freshness and numerator/denominator, then spot-check it against source rows.
3. **How do you automate report generation from versioned data with visual regression and artifact upload?** Pin the environment, version the input snapshot and code, run data-quality/unit tests, generate figures and report from one command, compare golden images with a documented tolerance, retain build/run ID and outputs in CI, and publish only after privacy/accessibility review.
