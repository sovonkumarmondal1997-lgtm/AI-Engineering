## Conventions stated once, used everywhere

- **Claims policy.** Every claim about learning efficacy, hiring, reproducibility rates in the literature or industry, the "best" tracking tool, or a seed count is exactly one of: (a) cited research/documentation tagged `[VERIFY]` with limits; (b) practitioner opinion/rule of thumb tagged `[JUDGEMENT]` or `HEURISTIC`; (c) a verifiable statement about mathematics, code, or the tree; or (d) omitted. **No claim that any tool or practice "guarantees" reproducibility; no prevalence statistic about irreproducible results.** Durations `[ASSUMPTION]`; sizes `[ILLUSTRATIVE]`.
- **Correctness policy.** Every worked example and key is verified **two independent ways**: (1) a hand derivation in the text, and (2) an independent computation — **exact (`Fraction`/`decimal`/`math.fsum`/enumeration) wherever possible**, otherwise `numpy`/`scipy` with a **stated tolerance and reason**, or simulation with stated `n`, seed, replicates, interval. **Every tool in the module is implemented as a short spec-literal reference and cross-checked against the standard library, NumPy, and SciPy on tiny and random inputs.** A library function is never the sole oracle for a claim about that function.
- **Proof policy.** Where Section 6 says "proof", write it in full: statement, hypotheses, every step justified, closing "where each hypothesis was used". **Heuristics are labelled `HEURISTIC` with their measured behaviour on a stated generator.** Where a result is `CITED [VERIFY]`, say which and give a numerical sanity check.
- **Reproducibility levels (the module's central vocabulary, used everywhere).** **(R0) not reproducible; (R1) re-runnable: the code runs again on the recorded inputs; (R2) bitwise reproducible: identical outputs (hashes) on the same environment; (R3) statistically reproducible: the distribution of the metric over seeds is the same within stated intervals, on the same or a different environment; (R4) conclusion reproducible: the comparison's decision survives changes of seed, split, and environment.** **Every example and every claim states which level it targets and which it achieved; "reproducible" without a level is a defect.**
- **Run identity convention.** **A run is identified by a tuple `(code, data, config, environment, seeds)`; the run record stores, for each element, either an immutable content hash or an explicit "unrecorded" marker; a result is attributed only to the recorded tuple.** The 5A-00 manifest fields are reused and extended; **the schema carries a version and a migration rule**.
- **Evaluation-protocol and leak-free convention (inherited from 5A-00 to 5A-10).** The eight-item protocol card and the seven-item leak-free protocol apply to every tracked experiment; **tracking never changes what is fitted where: every learned statistic is fitted on training rows only, and the test set is touched once and that touch is itself logged.** Every example states which items it exercises; **an example that violates one is labelled as a counterexample.**
- **Experiment card (the module's central reporting convention; every tracked experiment is stated in this form).** **the question and the decision it supports; the pre-registered hypothesis and comparison plan (written before runs); the run tuple conventions (code version, dataset snapshot hash, config hash, environment fingerprint, seed design); the target reproducibility level and the achieved level with evidence; the number of runs attempted, completed, failed, and excluded (with reasons); the metrics, their conventions, and intervals; the paired comparisons and multiplicity control; the selection procedure and its budget; the report (including negative and null results); known threats; the artifact locations and hashes.** Reporting an experiment without these fields is a defect; every worked example ends with the filled card.
- **Notation convention.** A run `r = (c, d, g, e, s)` with code `c`, data `d`, configuration `g`, environment `e`, and seed material `s`; a metric `m(r)` and a metric distribution over seeds `M(c, d, g, e)`; content hash `H(·)` (SHA-256 unless stated) with canonical serialisation `ser(·)`; `ln` natural; sums versus means always stated; indices 1-based in text with the 0-based Python translation side by side; plain-text math with Unicode, **no LaTeX**.
- **Estimation policy.** Every reported experimental quantity carries `n` (the number of independent seeds/splits/datasets), the seed design, and an interval: **seed-to-seed spread reported as the distribution (median, spread, and a `t` or bootstrap interval for the mean with the replicate count); paired differences for comparisons on the same seeds/splits (5A-07); a permutation baseline where a lift is claimed; multiplicity control when several comparisons are reported; and always the number of configurations tried.** No best-seed, best-config, or best-run reporting.

Named results (the birthday bound, floating-point error analysis, the winner's curse, Bonferroni/Holm/Benjamini–Hochberg, Merkle trees) are referred to **by name and own-words statement only**; never reproduce a paper's, textbook's, or tool's wording, tutorials, or exercise sets.

## Unit 4 — Systematic run comparison and avoiding cherry-picking

- **L1:** **comparing two models or settings means comparing *distributions* over seeds and splits, not two numbers: one run per config is one draw; the difference you see may be noise**; **cherry-picking in plain words: reporting the run, seed, metric, split, or comparison that looks best and hiding the rest; it need not be dishonest to be harmful (trying many things and reporting the winner is enough)**; **the forking-paths problem (recall 5A-07): every analysis choice (seed, split, metric, preprocessing, config) is a fork; the more you try, the more likely something looks good by chance; the cure is to decide the plan first and count everything tried**; **a first worked example by hand: two configs `A` and `B` with the same true mean; ten seeds each; the best-of-ten for each; `B` "wins" by luck in half the repetitions; the paired comparison over the same seeds shows no reliable difference**; **the minimum honest comparison: the same seeds/splits for both configs (paired), the number of seeds stated, the mean difference with an interval, and all runs reported**; ≥ 3 worked examples.
- **L2:** **in depth (derived/measured)**: **(1) pre-registration (a plan file written and hashed *before* running: the question, the metrics and their direction, the primary comparison, the seed set and split design, the number of runs, the stopping rule, the analysis method, the multiplicity plan, the exclusion rules;
