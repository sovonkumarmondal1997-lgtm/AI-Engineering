## Unit 1 — What dynamic programming is
- **L1:** the **idea**: solve a problem by solving **smaller versions of it** and **reusing** their answers instead of recomputing them; **naive Fibonacci** as the motivating example (the recursion tree, **call counts measured** for n = 10…35, growth by the golden ratio observed numerically; S3-05 Unit 6 link) and its **memoized** and **iterative** versions; the two properties that make DP applicable — **overlapping subproblems** (the same subproblem is needed many times) and **optimal substructure** (an optimal answer is built from optimal answers to subproblems) — each with a drawn example and a **non-example** (merge sort has no overlap — divide and conquer; longest *simple* path lacks optimal substructure — counterexample drawn); **three flavors** of DP answers: **counting** (how many ways), **optimization** (min/max), **feasibility** (is it possible); first problems: **climbing stairs**, **Fibonacci**, **minimum cost climbing stairs**, **coin change (fewest coins)** introduced as a recursion first; hand trace of a table filled left to right.
- **L2:** the **five-step DP recipe**: *(1) define the state, (2) write the transition (the recurrence), (3) set the base cases, (4) choose the evaluation order, (5) read the answer* — applied end to end to climbing stairs, house robber (preview), coin change (min coins and number of ways), and **minimum path sum** (preview of Unit 8); the **DP table as a DAG** (states = vertices, dependencies = edges; **bottom-up evaluation = topological order**, **top-down = DFS with caching** — S3-08 Unit 4 link: a DP is exactly a longest/shortest/counting path computation on a DAG of states); **complexity = number of states × work per state**, demonstrated by counted states and transitions; **DP vs greedy vs divide and conquer vs backtracking** decision table with a **concrete greedy failure**: coin change with coins `{1, 3, 4}` and amount 6 (greedy picks 4+1+1 = 3 coins; optimal is 3+3 = 2 coins) and coin systems where greedy happens to work (stated; proof deferred to module 11); **recognition signals** ("number of ways", "minimum/maximum cost", "is it possible", "longest/shortest subsequence", "partition", "choose or skip" — each with a counter-signal); **brute-force oracles** by enumeration (`itertools`, recursion) for every example; **reconstruction** by storing the **choice** at each state (parent pointers) and walking back, compared with re-deriving choices from the table; **big counts** (Python ints are arbitrary precision; the modulo convention `10**9 + 7` used by many problem statements and why it is irrelevant for correctness in Python but relevant for performance and for portability — state it honestly).
- **L3:** **proof of the DP method**: (a) **correctness by induction on the evaluation order** (if every dependency of state `s` is evaluated before `s` and each is correct, the recurrence makes `s` correct — write the template once and reuse it); (b) **optimal substructure formalized** (the "cut-and-paste" argument: if an optimal solution used a suboptimal sub-solution, replace it and improve — contradiction; and where it **fails**: longest simple path, shortest path with a parity or resource constraint **not encoded in the state** — counterexamples; the fix is to enlarge the state); (c) **overlapping subproblems quantified** (number of distinct subproblems vs number of calls: Fibonacci n + 1 distinct vs Θ(φⁿ) calls — derive); (d) **complexity** = |states| × cost(transition), with the **state-space size** as the real design constraint (a table of typical sizes and their feasibility in Python for 10⁶–10⁷ operations `[ILLUSTRATIVE — measure yours]`); (e) **Bellman's principle of optimality** named with attribution (`[VERIFY]` wording) and its relation to optimal substructure; (f) **why a recurrence must be well-founded** (states must form a DAG — a cyclic dependency means DP does not apply directly; shortest paths in cyclic graphs need Dijkstra/Bellman–Ford, S3-08/module 12); (g) **counting DP correctness** (the partition of the solution set by the last choice is a bijection — no overcounting, no omission — the argument that most counting bugs violate).
- **L4:** **engineering**: **how to approach an unfamiliar problem** (a written procedure: write brute force, find repeated subproblems, define the state, derive the recurrence, test against brute force, then optimize), **common failure modes** (state too small to capture the constraints; state too large to afford; wrong base; wrong order; double counting; confusing "ending at i" with "up to i"), **DP in production** (where it appears: diffing and fuzzy matching, segmentation, scheduling, budgeting, decoding — named at the concept level, **no company claims**), **cost awareness** (O(nm) tables and attacker-controlled sizes: **enforce size limits before allocating**; tested), **testing methodology** (every DP against a brute force on exhaustive small inputs plus seeded random; property tests such as monotonicity of the optimum in the budget; top-down and bottom-up agree), **mutation lab** (wrong base case, off-by-one in the recurrence, wrong min/max, wrong order) with no surviving mutants; documentation of the DP design card as a code docstring; coaching approach ("say the state in one sentence; if you cannot, you do not have a DP yet").

## Unit 2 — Memoization vs tabulation
- **L1:** the two implementations of the same recurrence: **top-down (memoization)** — write the recursion, cache each result by its arguments, return the cached value on repeats — and **bottom-up (tabulation)** — fill a table from the smallest states upward; both on Fibonacci and climbing stairs; `functools.cache` and `functools.lru_cache(maxsize=None)` (decorator usage, `cache_info()`, `cache_clear()`); a hand-written dictionary memo; **hit/miss counts** read from `cache_info()`; the **hashable-arguments requirement** (a list argument raises `TypeError`).
- **L2:** **converting** a recursive solution into both forms for coin change (min coins), longest common subsequence (preview), and 0/1 knapsack (preview); **choosing the table type** (list, list of lists, `dict` for sparse states, `array`); **evaluation order for tabulation** (derived from the dependency DAG: increasing `i`; for 2-D states, row by row; for interval states, by length); **memo key design** (tuples of ints; never mutable arguments; encode state compactly; **index-based** state instead of passing slices — S3-05 Unit 1 link); **top-down advantages** (computes only **reachable** states — demonstrate with a problem where far fewer than all states are reached — and is often the quickest to write) and **disadvantages** (recursion depth, call overhead, harder space optimization); **bottom-up advantages** (no recursion limit, predictable memory, easy rolling arrays) and **disadvantages** (may compute unreachable states; needs a correct order up front); **recursion limits** (`RecursionError` on n = 10⁴ for linear memoized recursion — demonstrated; remedies: tabulate, or run with an explicit stack, or raise the limit **with a thread and a bounded stack size** — `[VERSION-SENSITIVE]`, with `setrecursionlimit` always restored in `finally`); **counting recursion calls and states** (`cache_info().misses` = number of states computed); **reconstruction in both styles**; a **generic memo decorator** with instrumentation (counts calls, hits, states; resettable); **the `lru_cache` memory trap** (`maxsize=None` grows without bound; caching **methods** keeps `self` alive — S3-04 Unit 5 link) and the per-call local memo alternative (a closure over a fresh `dict`) for functions whose cache must not persist across inputs; **shared-memo contamination** (a module-level memo reused across different problem instances silently returns wrong answers — demonstrated with two different coin sets).

## Unit 3 — One-dimensional DP patterns

## Unit 12 — Bitmask dynamic programming introduction

## Unit 13 — Space optimization in dynamic programming
- **L1:** **why optimize space**: many DP tables are **O(n·m)** but each cell depends only on a **bounded window** of previous cells; the **rolling array** idea — keep only the rows (or values) still needed; first examples: **Fibonacci with two variables** (O(1) space), **climbing stairs**, **LCS length with two rows** (O(min(m, n)) space); a before/after **memory measurement** with `tracemalloc`; the trade-off: **you lose the full table, so reconstruction becomes harder**.
