## Unit 1 — Range query problem fundamentals
- **L1:** the **range query problem**: given an array `a[0 … n−1]`, answer many questions of the form **"what is `f(a[l], …, a[r−1])`?"** — sum, minimum, maximum, gcd, xor, count of a value, and so on — possibly **interleaved with updates** (**point update**: change one element; **range update**: change every element in a range); the **naive solution** (loop over the range — `O(n)` per query) and why it is too slow for `q` large (`O(n·q)`); **half-open ranges `[l, r)`** and why the module uses them (length `r − l`; adjacent ranges concatenate; empty range natural); **the four problem classes** — *static queries*, *point updates + range queries*, *range updates + point queries*, *range updates + range queries* — each with an example; **offline** (all queries known up front) vs **online** (answered as they arrive); a first **naive class** `NaiveRangeQuery` (the oracle used throughout the module) with counted element touches; hand-worked examples.
- **L2:** **the operation algebra** (taught as the module's organizing idea): a **monoid** is an operation `combine` that is **associative** (`(a·b)·c = a·(b·c)`) with an **identity** `e` (`e·a = a·e = a`); **commutative** means `a·b = b·a`; a **group** adds **inverses** (`a·a⁻¹ = e`); an operation is **idempotent** if `a·a = a`; classify the standard operations in a **table**: **sum** (group, commutative), **xor** (group, commutative, each element its own inverse), **min/max** (idempotent commutative monoid, no inverse), **gcd** (idempotent commutative monoid), **bitwise and/or** (idempotent), **product mod a prime** (group if nonzero; note zero), **count/frequency vectors** (group under addition), **string concatenation** and **matrix multiplication** and **function composition** (**non-commutative monoids** — the stress test for order handling), **(sum, count) pairs**, **(min, argmin) pairs with a tie rule** (monoid), **maximum subarray sum composite `(sum, best_prefix, best_suffix, best)`** (monoid — S3-02 Unit 11 link), **average** and **median** (**not monoids** — averages must be carried as `(sum, count)`; medians are not decomposable — **demonstrated with a counterexample**); **a `Monoid` class** (identity, combine, optional inverse, flags) and a **law checker** (`check_associative`, `check_identity`, `check_commutative`, `check_idempotent`, `check_inverse` — **exhaustive over a small sample domain** with clear failure reports) used throughout the module; **which structure needs which laws** (preview table: prefix sums → group; Fenwick → group for range queries (prefix-only for monoid); segment tree → monoid; sparse table → idempotent monoid for `O(1)`; Mo's → add/remove maintainable; difference arrays → group); **update costs with naive structures** (point update `O(1)` but query `O(n)`; precomputed prefix sums: query `O(1)` but update `O(n)`); **workload parameters** `n`, `q`, `u`, and **total cost** `T = build + q·t_query + u·t_update`; **recognition signals** ("sum over a subarray", "minimum in a window", "how many elements ≤ x in a range", "add `v` to a range"); **input validation** (`0 ≤ l ≤ r ≤ n`; integers; the **negative-index wraparound trap** — `a[l:r]` with negative `l` silently works in Python and is a bug here); **error taxonomy** (`RangeError`, `NotAMonoidError`).
- **L3:** **proofs**: (a) **why each structure's required laws are necessary** — exhibit, for each law, an operation that violates it (**subtraction is not associative; averaging is not associative; max-with-ties-by-index is associative only with a consistent tie rule**) and the **concrete wrong answer** a segment tree gives for it (**demonstrated by running the structure with the bad operation against the oracle**); (b) **monoid law consequences** (the fold of a sequence is independent of how it is parenthesized — **proof by induction**; hence **any decomposition of a range into adjacent blocks gives the same answer if `combine` is associative and blocks are combined in order**; **commutativity is needed only if blocks are combined out of order**); (c) **identity element's role** (empty ranges; padding for non-power-of-two sizes); (d) **half-open range algebra** (`[l, m) ∪ [m, r) = [l, r)`; length `r − l`; **split identity `query(l, r) = combine(query(l, m), query(m, r))`** for any `l ≤ m ≤ r` — used later as a **metamorphic test**); (e) **cost model** (`n`, `q`, `u`; build/query/update; counted element touches); **the break-even analysis between naive and prefix-sum approaches** (`q` queries and `u` updates: naive `q·n`; prefix-sums-with-rebuild `u·n + q`; derive when each wins — **measured**); (f) **lower-bound landscape named, cited `[VERIFY]`** (dynamic prefix-sum queries require `Ω(log n)` per operation in the cell-probe model — **cited only**); (g) **idempotence enables overlapping decompositions** (`combine(x, x) = x` — proof that overlapping two ranges covering `[l, r)` is safe) — the basis of the sparse table; (h) **invertibility enables subtraction** (`query(l, r) = P(r) · P(l)⁻¹`) — the basis of prefix sums and Fenwick range queries.

## Unit 4 — Fenwick tree (binary indexed tree)
- **L1:** the **problem**: **point updates and prefix/range sums, both fast** — prefix sums have `O(n)` updates; a plain array has `O(n)` queries; the **Fenwick tree** (**binary indexed tree, BIT**) gives **`O(log n)` for both**; the **key idea**: store, at each index `i` (1-based), the sum of a **block of elements ending at `i`** whose length is the **lowest set bit** of `i` (`lowbit(i) = i & −i` — S3-10 Unit 3 recall); a picture of `n = 8` showing which block each cell covers (`t[1] = a[1]`, `t[2] = a[1..2]`, `t[3] = a[3]`, `t[4] = a[1..4]`, …, `t[8] = a[1..8]`); **prefix sum query**: start at `i`, add `t[i]`, move to `i − lowbit(i)`, stop at 0; **point update**: add `delta` to `t[i]`, move to `i + lowbit(i)`, stop when `i > n`; hand traces of both on `n = 8`.
- **L2:** a complete **`FenwickTree` class** (1-based internal array of size `n + 1`; **0-based public API**, half-open ranges `range_sum(l, r) = prefix(r) − prefix(l)` where `prefix(k)` sums the first `k` elements), **`add(i, delta)`**, **`set(i, v)`** (via the current value or a mirrored array — **state the memory/time choice**), **`prefix(k)`**, **`range_sum(l, r)`**, **linear-time build** (**`t[i] += a[i]; j = i + lowbit(i); if j ≤ n: t[j] += t[i]`** — implemented and compared with `n` calls to `add`, `O(n)` vs `O(n log n)`, by counted steps), **why the structure is 1-indexed** (`lowbit(0) = 0` makes the update loop **infinite** — **demonstrated with a hang-proof guard**), **a generic `FenwickTree(group)`** (works for any commutative group: `+`, `xor`, modular addition; **requires an inverse for range queries**; for a monoid only prefix queries are available — **min/max Fenwick for prefix-only with non-decreasing updates is named**), **tree-structure printers** (parent/child relationships: the **query parent** `i − lowbit(i)` and the **update parent** `i + lowbit(i)`), **exact `Fraction`/int values**, **validation** (`0 ≤ i < n`, `0 ≤ l ≤ r ≤ n`), **comparison with prefix sums and the naive structure** by counted element touches across update-heavy, query-heavy, and mixed workloads, **running example**: live counters with windowed totals.
- **L3:** **proofs written in full**: (a) **responsibility invariant**: **`t[i] = Σ_{j = i − lowbit(i) + 1}^{i} a[j]`** (stated as the representation invariant; **the validator `_check_invariants()` recomputes every cell from a mirrored array**); (b) **prefix query correctness** (the intervals visited by repeatedly subtracting `lowbit` partition `[1, i]` into disjoint blocks: **each step removes the lowest set bit, so the block `(i − lowbit(i), i]` is followed by blocks covering `[1, i − lowbit(i)]` — induction on the number of set bits**); (c) **update correctness** (**the cells that cover position `p` are exactly `p, p + lowbit(p), …` — proof: `i` covers `p` iff `i − lowbit(i) < p ≤ i`; show that the set of such `i` is generated by repeatedly adding the lowest set bit**); (d) **cost bounds**: **query takes `popcount(i) ≤ ⌊log₂ n⌋ + 1` steps; update takes at most `⌊log₂ n⌋ + 1` steps** (each step strictly increases the number of trailing zeros of the index — proof); (e) **linear build correctness** (processing `i` in increasing order, `t[i]` is complete when `i` is reached because every cell `i′ < i` that contributes to it has already propagated; **invariant: after processing `i`, `t[j]` for `j ≤ i` is final**); (f) **why the `lowbit` trick works with two's complement** (`−i = ~i + 1`; `i & −i` isolates the lowest set bit — S3-10 Unit 3 proof recalled); (g) **space `n + 1`** and **why group inverses are needed for range queries** (Unit 1 algebra) **while a prefix-only monoid Fenwick needs no inverse but supports only prefix queries (and only compatible updates)**; (h) **comparison of bounds** with segment trees (constants and memory `n` vs `2n`/`4n`).
- **L4:** **engineering**: **performance in Python** (counted steps; the `i & −i` idiom inlined vs helper function; `array('q')`/lists; **typical per-operation cost versus a list-of-lists segment tree** — measured; `[ILLUSTRATIVE]`), **exactness and large values** (Python ints; `Fraction`; **float Fenwick sums accumulate rounding error in an order-dependent way — demonstrated**), **hostile inputs** (`i = −1`, `i = n`, huge `n`, non-integer deltas, `bool` indices — validation; **`n = 0` edge case**), **memory estimator** (`n = 10⁷` ⇒ `~80 MB` for Python ints in a list — **measured; use `array`**), **concurrency** (single-writer; compound read-modify-write not atomic — precise statement), **explanations** (`explain_prefix(k)` lists the blocks used; `explain_update(i)` lists the cells touched), **integration with the running example** (event counters per time slot with windowed totals), **testing**: oracle = naive array on **all arrays of length ≤ 8 over `{0, 1, 2}`, all `[l, r)`, and all sequences of ≤ 3 updates interleaved with all queries**; **invariant validator after every operation**; linear build vs repeated adds equality; generic-group Fenwick with `xor` vs naive; property tests (split identity; update then inverse update restores all queries; `range_sum(0, n)` = total); **mutation lab** (0-based internal indexing; `i + lowbit` vs `i − lowbit` swapped; off-by-one in `range_sum`; wrong loop bound `i < n` vs `i ≤ n`; build propagating before completion) with no surviving mutants; **regression guard** on counted steps (≤ `⌊log₂ n⌋ + 1`); documentation of conventions; coaching approach ("each cell is responsible for a block that ends at it").

## Unit 6 — Segment tree fundamentals

## Unit 8 — Lazy propagation for range updates
- **L1:** the **problem**: **range updates (add `v` to every element of `[l, r)`; or assign `v`) *combined with* range queries** — updating each element is `O(n)`; the **idea of laziness**: **don't update the children now; leave a *pending tag* on the node that covers the whole updated range and apply it only when a later operation needs to look inside**; each node stores **an aggregate and a lazy tag**; the **invariant in words**: *a node's aggregate is always correct for its own range; a non-empty tag means its children have not yet received the update*; **push-down** (before descending into a node, send its tag to both children and clear it); hand trace of a range-add on `[1, 6)` of an 8-element tree showing which nodes receive tags and which do not; first Python snippet for **range add + range sum**.
- **L2:** a **generic `LazySegmentTree`** parameterized by **(a) the value monoid `(identity, combine)`, (b) the tag monoid `(tag_identity, compose)`, and (c) `apply(tag, node_value, node_length)`** (the **length argument** is needed for sum under add/assign); **implementations (each with oracle and tests)**: **range add + range sum** (`apply(add v, s, len) = s + v·len`), **range add + range min/max** (`apply(add v, m) = m + v` — **no length needed**), **range assign + range sum** (`apply(set v, s, len) = v·len`), **range assign + range min/max**, **range add and assign combined** (**tag as a pair or an affine map `x → a·x + b` with composition `(a₂, b₂)∘(a₁, b₁) = (a₂a₁, a₂b₁ + b₂)` — and the special assign tag `(0, v)`; non-commutative composition order**), **range multiply + range add + range sum mod `p`** (affine tags), **range flip + count of ones** (xor tag: `apply(flip, (ones), len) = len − ones`; tag composition `flip∘flip = id`), **range set to value + range query max**; the **recursive operations** (`range_update(l, r, tag)`, `query(l, r)`, both pushing down on the way); **`push_down(node)`** implementation details (apply to children, compose into children's tags, clear); **`_check_invariants()`** (**with all pending tags conceptually applied, each node's aggregate equals the fold of the *true* array values over its range — the validator reconstructs true values by pushing tags down on a copy**); **non-propagating ("permanent tag") variant for commutative add on min/max** (**tags never pushed; queries add the tags of ancestors — implemented as an optional optimization with its preconditions**); **counted node visits per operation** (verifying `O(log n)`); **the running example**: **bulk corrections** (add an offset to a time window) with live window sums and extrema.
- **L3:** **proofs written in full**: (a) **the lazy invariant** (**for every node `v`: `agg(v)` equals the fold over `v`'s range of the true values *as modified by all tags on `v`'s proper ancestors' paths that have not reached `v` yet*, composed in root-to-`v` order — precisely: the true aggregate of `v`'s range = `apply(compose of tags on ancestors from the root down to the parent of v, agg(v), len(v))`**); **range update and query preserve it** (induction on the operation's recursion; **push-down preserves the invariant because `apply` distributes over `combine`**); (b) **the homomorphism requirement**: **`apply(t, combine(x, y), len_x + len_y) = combine(apply(t, x, len_x), apply(t, y, len_y))`** — **proved for each shipped (value, tag) pair; counterexample for an invalid pair** (e.g., `add` with a **product** aggregate without exponentiating; **range add + range max-count without carrying counts**); (c) **tag-composition associativity and identity** (`apply(compose(t₂, t₁), x) = apply(t₂, apply(t₁, x))` — **action property; proof for add, assign, affine, flip**), **non-commutativity of assign and add** (counterexample for wrong order); (d) **complexity**: **each operation visits at most `4⌈log₂ n⌉` nodes plus pushes at most two children per visited node — `O(log n)`** — **proof via the same canonical-decomposition argument as Unit 6**; (e) **build `O(n)`**; (f) **why correctness fails without push-down before descending** (stale child values — **demonstrated**); (g) **memory** (`4n` aggregates + `4n` tags) and **the tag-identity convention for "no pending tag" when the identity is a legal tag value** (**use a separate `has_tag` flag for assign: `v = 0` is a valid assignment — the classic bug**); (h) **permanent-tag variant correctness** (valid only when tags commute with each other and with `combine` — **min/max under add**).
- **L4:** **engineering**: **choosing the representation of tags** (affine pairs for generality; specialized tags for speed; **counted node visits first**), **exactness** (`Fraction`/int; **modular tags with explicit modulus**; float add on sums accumulates drift — demonstrated), **range assign vs add interactions** (the `has_tag` flag; **composition order tests**), **hostile inputs** (invalid tags; non-homomorphic `apply` — **a homomorphism checker over small samples run at construction in debug mode**; out-of-range updates), **recursion** (depth `O(log n)`; **iterative variant in Unit 9**), **explanations** (**dump the tree with tags to debug**), **performance in Python** (tag objects vs parallel arrays; **counted pushes**; `[ILLUSTRATIVE]`), **applications** (calendar/capacity bulk edits, bulk metric corrections, range resets — conceptual), **testing**: oracle = **naive array with element-wise updates** on **all arrays of length ≤ 5 over `{0, 1, 2}` and *all sequences of up to 4 operations drawn from {range add, range assign, range query} over all `[l, r)`*** — **exhaustive** for each (value, tag) pair shipped; the homomorphism checker validated on valid and invalid pairs; seeded random with adversarial interleavings (assign then add then query; overlapping ranges; full-range ops; single-element ops); property tests (split identity; update then inverse update restores queries for add; assign idempotence; invariant validator after every operation); **mutation lab** (missing push-down before query; push-down without composing into existing child tags; wrong composition order; forgetting the length factor; `has_tag` omitted for assign-0; clearing the tag before applying) with no surviving mutants; **regression guard** on node visits and pushes; documentation of the (value, tag, apply, compose) quadruple and its proofs; coaching approach ("a tag is a promise the children have not heard yet").

## Unit 9 — Iterative segment trees
- **L1:** why an **iterative (bottom-up) segment tree**: no recursion, **half the memory** (`2n` slots), and **much smaller constants** — the standard "efficient segment tree"; the **layout**: the array `t` of length `2n`, **leaves at positions `n … 2n − 1`** (leaf for `a[i]` at `n + i`), **internal node `i` = `combine(t[2i], t[2i + 1])`** for `i = n − 1 … 1`; picture for `n = 8` (a perfect tree) and note for `n = 6` (**a "forest" of perfect subtrees**; node 1 is **not** the whole-array aggregate when `n` is not a power of two); **build**: a single loop; **point update**: set the leaf, then **walk up** recomputing `t[p >> 1]`; **point query**: read `t[n + i]`; first hand-run on `n = 8`.
- **L2:** the **bottom-up range query for half-open `[l, r)`** (**`l += n; r += n; while l < r: if l & 1: left = combine(left, t[l]); l += 1; if r & 1: r −= 1; right = combine(t[r], right); l >>= 1; r >>= 1; return combine(left, right)`** — **left and right accumulators keep the order for non-commutative operations**; the **commutative shortcut** (single accumulator) **shown to fail for non-commutative monoids**), **point update** (`p += n; t[p] = v; while p > 1: p >>= 1; t[p] = combine(t[2p], t[2p + 1])`), **an `IterativeSegmentTree` class** (generic monoid; `n` arbitrary), **verification that the structure works for every `n` ≤ 64** (not only powers of two) **with non-commutative operations** (**exhaustive over all `n`, all `[l, r)`** — **`[VERIFY]` the claim against a cited formulation and prove or exhibit the argument in L3**), **power-of-two padded variant** (pad with identity to `2^k`; root is the whole-array aggregate; **binary descent from the root for search problems** — first-index-≥-x, k-th — **implemented iteratively**), **iterative lazy propagation** (**the standard approach: compute height `h = n.bit_length()`; `push(p)` from the top for the boundary leaves `l` and `r − 1`; `apply(node, tag, size)`; **`build(p)` upward after updates** — implemented for range add/range sum and range add/range min as an advanced variant with its invariant; **compared with the recursive lazy tree of Unit 8**), **recursive vs iterative comparison** (counted node visits and combine calls; memory `2n` vs `4n`; **constant factors measured**; `[ILLUSTRATIVE]`), **min/max/sum/gcd/xor instances**, **non-commutative demonstrations** (concatenation, affine composition), **applications**: **fast point-update/range-query workloads** (the running example's live window min/max at high rates).
- **L3:** **proofs written in full**: (a) **invariant**: **for `i` in `[1, n)`, `t[i] = combine(t[2i], t[2i + 1])`; leaves hold the array; hence each internal node holds the fold over *its set of leaves in left-to-right order* — for perfect `n` that is a contiguous range; for general `n` the nodes whose leaf sets are *contiguous in array order* are exactly the ones the query uses** — **write the argument carefully and verify exhaustively**; (b) **query correctness** (**at each level, the loop invariant: `left` = fold of the already-claimed left-boundary nodes, `right` = fold of the claimed right-boundary nodes, and the unclaimed part of `[l, r)` is exactly the leaves under positions `[l, r)` at the current level; the `l & 1` / `r & 1` tests claim nodes that are *right children on the left boundary* and *right children just inside the right boundary*; termination when `l ≥ r`** — **induction on levels**), **the non-commutative order argument** (nodes claimed on the left are in left-to-right order; nodes claimed on the right are in right-to-left order and are prepended); (c) **correctness for non-power-of-two `n`** (**the claimed nodes only combine children that are both within the range's leaf sets; nodes that mix across the "wrap" are never used by a query — proof**; **cited `[VERIFY]` if a full proof is long, with the exhaustive verification for all `n ≤ 64`**); (d) **complexity**: **`O(log n)` per query and update — at most `2⌈log₂ n⌉` combines per query and `⌈log₂ n⌉` per update**; **`O(n)` build**; **space `2n`**; (e) **iterative lazy correctness** (**pushing from the top along the two boundary paths guarantees that every node claimed by the query or update has no ancestor with a pending tag affecting it — invariant**; **`build` upward restores aggregates after tags are applied** — proof); (f) **why padding to a power of two gives a proper tree and a meaningful root** (and the **cost: up to `2×` memory**); (g) **descent correctness on the padded tree** (as Unit 7); ## Unit 10 — Sparse table for static range queries
- **L1:** **static queries, `O(1)` each**: for **idempotent** operations (min, max, gcd, bitwise and/or) an array that is **never updated** can answer range queries in **constant time** after an `O(n log n)` precomputation; the **idea**: precompute answers for **all ranges whose length is a power of two** — `st[k][i]` = fold over `[i, i + 2^k)`; a **query `[l, r)`** of length `len = r − l` picks `k = ⌊log₂ len⌋` and combines **two possibly overlapping power-of-two ranges that together cover `[l, r)`**: `st[k][l]` and `st[k][r − 2^k]`; **why overlap is harmless for min/max** (**idempotence**: `min(x, x) = x`) **and harmful for sum** (counterexample: overlapping counts elements twice); picture for `n = 8`; hand-built table and a worked query; `k` via **`len.bit_length() − 1`** (S3-10) vs a precomputed log table.
- **L2:** a **`SparseTable` class** (generic over an **idempotent monoid**; **rejects non-idempotent operations unless used in the `DisjointSparseTable` mode — law-checked**), **build**: level 0 = array; **`st[k][i] = combine(st[k−1][i], st[k−1][i + 2^(k−1)])`** for `i + 2^k ≤ n`, **`O(n log n)` time and memory** (**estimator: `n = 10⁶` ⇒ ~20 million entries — infeasible in pure Python lists; cap and use `array` or fewer levels**), **query** `O(1)` (**half-open `[l, r)`, `l < r` required; empty range returns identity only if the monoid has one — **state policy**), **argmin/argmax sparse tables** (store indices; **tie rule — leftmost — must be consistent in `combine`; overlapping ranges still safe because the tie rule is idempotent**), **range gcd**, **range bitwise-and/or**, **non-idempotent operations: the `DisjointSparseTable`** (**for sum and other monoids: precompute prefix/suffix aggregates within blocks at each level so that any query combines two disjoint pieces in `O(1)`** — implemented; **`O(n log n)` build; `O(1)` query**) **and the simpler `O(log n)` decomposition query** (greedily taking the largest block: `O(log n)` for any monoid — S3-10 binary decomposition), **RMQ for LCA** (**Euler tour + sparse table: `O(n log n)` build, `O(1)` LCA — S3-06 Unit 14 and S3-12 Unit 7 recalled; implemented on a seeded rooted tree and verified against naive LCA**), **static frequency/majority-style queries** (named), **2-D sparse table** (named; `O(RC log R log C)` build — `[VERIFY]` statement), **running example**: static historical min/max over archived days with `O(1)` queries, **comparison table: sparse table vs segment tree vs Fenwick vs prefix sums** (build, query, update, memory, operation requirements).
- **L3:** **proofs written in full**: (a) **table invariant**: **`st[k][i] = fold(a[i : i + 2^k])` whenever `i + 2^k ≤ n`** (induction on `k`; associativity not even needed beyond splitting the block into two halves in order); (b) **query correctness for idempotent monoids**: with `k = ⌊log₂ (r − l)⌋`, the ranges `[l, l + 2^k)` and `[r − 2^k, r)` **cover `[l, r)`** (**since `2^k ≤ r − l < 2^{k+1}`, so `l + 2^k ≥ r − 2^k`**) **and both lie inside `[l, r)`**; **their combination equals the fold over `[l, r)` because every element appears at least once and idempotence + commutativity (or at least ordered overlap handling) make duplicates harmless** — **state precisely which laws are needed: for min/max/gcd (commutative idempotent) it is safe; for a non-commutative idempotent operation overlapping order matters — `[VERIFY]` and give the counterexample or the correct condition**; (c) **why sums fail** (counterexample); (d) **disjoint sparse table correctness** (**at each level, blocks of size `2^k` are split at their midpoint; for a query whose endpoints fall in different halves at the highest differing bit level, the answer is `suffix aggregate of the left half from l` combined with `prefix aggregate of the right half to r` — the level is `(l ^ (r − 1)).bit_length() − 1` — proof; S3-10 XOR-highest-differing-bit trick**), **`O(1)` query**; (e) **complexity**: build `O(n log n)` time **and space** (**why not `O(n)`: derive `Σ_k (n − 2^k + 1)`**), query `O(1)`; **`log` table correctness** (`log[i] = log[i >> 1] + 1`); (f) **cited improvements named `[VERIFY]`** (**`O(n)`-space `O(1)`-query RMQ via Cartesian trees and the ±1 reduction — Fischer–Heun; Bender–Farach-Colton for LCA ↔ RMQ — cited only**); (g) **the update problem** (a point update changes `O(n)` cells in the worst case — **counterexample/analysis: updating `a[0]` changes the entry `st[k][0]` and also `st[k][i]` for all `i` within `2^k − 1` before … — derive**); **why sparse tables are static**.
- **L4:** **engineering**: **memory control** (**levels as `array('q')`/lists; compute `k_max = n.bit_length() − 1`; refuse oversized `n` with a clear error**; **lazy/blocked sparse tables (sparse table over block minima + in-block scans) — `O(n)` memory trade-off — implemented as an advanced variant with counted costs**), **build speed in Python** (per-level list comprehensions/`map`; counted combines; measured), **hostile inputs** (`l ≥ r`; non-idempotent ops — **law checker**; NaN in min/max — **comparisons with NaN are always false, silently corrupting min/max — demonstrated; reject NaN**; `n = 0`), **immutability guarantees** (copy on build; documented static contract; `update` raises), **explanations** (`explain_query(l, r)` shows `k` and the two blocks), **applications** (RMQ for LCA; range-gcd queries; static dashboards; **suffix-array LCP queries named** — module 15), **testing**: oracle = naive on **all arrays of length ≤ 8 over `{0, 1, 2, 3}` and all `[l, r)` with `l < r`**; all `n ≤ 40` for min/max/gcd/and/or; disjoint sparse table vs naive for **sum and for a non-commutative monoid**; argmin tie-rule tests with duplicates; Euler-tour LCA vs naive on **all rooted trees up to 8 nodes**; property tests (query on a single element returns it; split-union identity holds for idempotent ops where defined — `query(l, r) = combine(query(l, m), query(m′, r))` for overlapping `m′ ≤ m`); **mutation lab** (`k` off by one; second block `r − 2^k + 1`; closed vs half-open; wrong level count `k_max`; non-idempotent op accepted; wrong tie rule) with no surviving mutants; **regression guard** on combines per query (`≤ 1`) and build cost (`n log n` fitted); documentation of conventions; coaching approach ("two overlapping powers of two always cover the range — if overlap is harmless").

## Unit 11 — Choosing between prefix sums, Fenwick, and segment trees
- **L1:** **choosing is analysis, not preference**: the **five questions** — *(1) What operation (and which laws does it satisfy: associative, commutative, invertible, idempotent)? (2) Are there updates — none, point, or range? (3) What queries — prefix, arbitrary range, k-th/search, or something non-decomposable?
