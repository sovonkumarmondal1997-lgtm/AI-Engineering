## Unit 4 — Coordinate compression
- **L1:** the **problem**: values can be **huge or sparse** (timestamps, IDs, coordinates up to `10⁹`) while only **`n` distinct values** matter; **compress** them to **ranks `0 … m − 1`** so arrays, Fenwick trees, and segment trees indexed by value become feasible; **how**: `vals = sorted(set(xs))`; `rank(x) = bisect_left(vals, x)`; hand example compressing `[900, 5, 10⁹, 5, 77]`; **what is preserved** (order and equality) **and what is not** (distances); first use: counting inversions with a BIT over ranks (S3-13 recall).
- **L2:** **variants** (each with pattern card, oracle, stress test): **dense rank** (ties share a rank) vs **ordinal rank** (ties broken by position) vs **competition rank** (named) — **choose by the question**; **inverse mapping** (`vals[rank]`), **compressing several arrays jointly** (shared coordinate space for queries and data), **compressing 2-D points** (compress `x` and `y` independently), **compressing interval endpoints** and the **"elementary segments" view** (the gaps *between* consecutive compressed coordinates are the units the sweep/difference array operates on, with **weights = real lengths** — S3-13 Unit 3 recall, implemented for difference arrays on huge ranges), **including neighbors (`x − 1`, `x + 1`) when adjacency matters** (e.g., "points at distance 1", cells touching a boundary), **order-agnostic ids** (a `dict` assigning ids in first-seen order) **vs order-preserving ranks** (when the order does not matter, a hash map is `O(n)` and simpler), **compressing strings/tuples** (lexicographic order via sorting), **offline queries with compressed thresholds** (`bisect_right` for "≤ x" and `bisect_left` for "< x" — **the rank rule decides**), **applications**: **BIT/segment tree over values**, **inversion counting**, **count of smaller elements to the right**, **LIS on large values** (S3-09/S3-13), **skyline and union-of-rectangles coordinates** (Unit 3), **difference arrays over huge coordinate ranges**, **graphs with sparse node ids** (dict mapping), **DP over large coordinates** (only interesting points), **"compress the time axis"** for event simulations.
- **L3:** **proofs written in full**: (a) **order-preserving map correctness** (`rank` is **strictly monotone on the set of distinct values**: `x < y ⇔ rank(x) < rank(y)` — proof), hence **any algorithm whose output depends only on the relative order and equality of the values is invariant under compression** (**theorem; proof by showing every comparison result is preserved**); (b) **what compression does not preserve** (**differences, sums, ratios, midpoints** — **counterexample**: a "sum within `D`" query is **not** invariant; the fix is to keep **weights** (elementary-segment lengths) or compress **thresholds as well**); (c) **rank rules for queries** (`count(x ≤ t) = bisect_right(vals, t)` on the **multiset** vs `rank` on the **distinct** set — **proof of equivalence and the duplicate pitfalls**); (d) **elementary-segment correctness** (an interval `[l, r)` in original coordinates covers **exactly the elementary segments between `rank(l)` and `rank(r)`**; weighted length = `vals[j+1] − vals[j]` — proof); (e) **complexity**: `O(n log n)` to compress, `O(log n)` per rank lookup (or `O(1)` via a dict for exact values), memory `O(n)`; (f) **adjacency-preserving compression with neighbor insertion** (inserting `x − 1`, `x`, `x + 1` for each point preserves distance-1 relations — proof; **size at most `3n`**); (g) **two-dimensional independence** (compressing `x` and `y` separately preserves **dominance** relations — proof; **does not preserve Euclidean distance**).
- **L4:** **engineering**: **memory and speed** (sort + dedupe + dict; `array`; **avoid `list.index`**), **exactness** (integers/`Fraction`; **float keys and NaN** — reject), **streaming/online compression** (**not possible in order-preserving form without knowing future values — online alternatives: balanced trees (S3-06) or offline two-pass**), **hostile inputs** (huge `n`; many duplicates; mixed types — validate), **explanations** (print the mapping), **API design** (a `Compressor` class with `fit`, `transform`, `inverse`, `rank_le`, `rank_lt`, immutable after fit; **fit-on-data+queries guidance**), **testing**: oracle = **run the algorithm on the original small-domain values vs the compressed values** (answers identical for order-only algorithms) on **all arrays of length ≤ 7 over `{0, 10, 10⁶, 10⁹}` and random subsets**; **weighted/elementary-segment applications vs direct simulation on small coordinate ranges**; rank-rule tests with duplicates (`<` vs `≤`); property tests (`inverse(transform(x)) = x`; monotonicity; idempotence on already-compressed data); **mutation lab** (`bisect_left` vs `bisect_right` swapped; ties broken as ordinal when dense was required; missing neighbor insertion; unweighted segments where weights were required) with no surviving mutants; **regression guard** on counted operations; documentation of rank rules; coaching approach ("which questions depend only on order?").
- **Must include:** dense/ordinal rank compressors with the rank-rule proof, joint compression of data and queries, 2-D compression, elementary-segment compression with weights and neighbor insertion, applications (BIT over values, inversion counting, difference array on huge ranges), the order-invariance theorem with proof and the **distances-not-preserved counterexample**, an all-small-domain invariance oracle suite, a mutation lab, and the running example's compressed timestamp analytics.

## Unit 5 — Invariants and proof-driven problem solving
- **L1:** an **invariant** is a statement that stays true as an algorithm or process runs; a **monovariant** is a quantity that **only goes one way** (always decreases or always increases) and so proves the process **ends**; the habit: *before coding, state what stays true*; first examples: **loop invariant for linear search/two pointers** (recall S3-01/S3-03), **a process that must terminate** ("repeatedly replace the two largest by their difference" — monovariant: the sum or the count), **parity**: "can you reach all zeros by flipping pairs?"; hand-checked invariants on small cases.
- **L2:** the **proof-technique toolkit** with a **template and a worked, tested example for each**: **(1) loop invariants** (initialization, maintenance, termination — in-place partitioning, remove duplicates in a sorted array), **(2) monovariants/potential functions** (process termination; **bubble sort swaps = inversions** as a potential argument; bound on the number of operations), **(3) invariants of state machines for impossibility proofs** (**parity/coloring**: domino tilings of a chessboard with removed corners — **S3-08 Unit 8/9 recall**; **sliding-puzzle solvability parity** — S3-12 Unit 13 recall; **"can this configuration ever be reached?"**), **(4) extremal principle** (consider the smallest/largest element in a counterexample), **(5) pigeonhole** (guaranteed duplicates: **duplicate in `n + 1` numbers from `1 … n`** — S3-03 Unit 6 recall), **(6) conserved quantities** (**sum/gcd/xor invariants**: **water-jug reachability ⇔ divisibility by `gcd`**; **"make all elements equal by operations"**; **Nim as an xor invariant** — S3-10 recall), **(7) induction and strong induction** for recursive algorithms (recall), **(8) the contrapositive/minimal counterexample** (S3-11 recall); **problems** (original statements, each with an oracle and a verification): **light-bulb toggling (which bulbs are on?
