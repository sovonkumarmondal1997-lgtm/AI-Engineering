## Conventions stated once, used everywhere

- **Claims policy.** Every claim about learning efficacy, study method, hiring, role requirements, tool/statistic popularity, "industry standard" status, tool maintenance, drift prevalence, thresholds, window sizes, significance levels, or superiority is exactly one of: (a) cited from a T1/T2 source tagged `[VERIFY]` with its limits; (b) practitioner opinion tagged `[JUDGEMENT]`; (c) a verifiable statement about code, a derivation, a measurement, a simulation, or the repository tree; or (d) omitted. **No success rates, no outcome guarantees, no statements about what any named company does, no invented quotes or anecdotes, no rankings, no drift-prevalence figures, no tool performance figures.** All durations are `[ASSUMPTION]` templates; **all traffic rates, drift sizes, label delays, and costs in examples are `[ILLUSTRATIVE]` parameters or planted values labelled as such**.
- **The evidence-label convention (reused from `../09-…`, restated once).** Every statement about a system's behaviour carries exactly one label: **`MEASURED`** (observed on this machine, for this workload and configuration, with repetitions and an interval), **`SIMULATED`** (a seeded model or planted-incident replay with stated assumptions; validated against `MEASURED` data where any exists), **`DOCUMENTED`** (stated in named official documentation for a stated version and date; not independently verified), or **`NOT ASSESSED`**. **A detection rate, delay, false-alarm rate, or performance figure without a label is a defect. Results on planted incidents are `SIMULATED` evidence about the planted family only.**
- **The monitoring-signal-card convention (MSC; defined once; a course convention).** **Every monitored signal — a metric, a drift statistic, a quality check, a performance estimate, a service SLI — is specified by a *signal card* with: (1) *name and purpose* (what decision or action it informs); (2) *definition* (the exact formula and the data it reads, with units); (3) *reference* (what it is compared with: a versioned reference window, a baseline, or an absolute rule — `reference-window convention` below); (4) *window and step* (length, tumbling or sliding, event-time vs processing-time, late-data rule); (5) *statistic and threshold* (with the rationale: an effect size of interest, a false-alarm budget, and a detection-delay target — not a conventional cut-off); (6) *minimum sample size* (below which the signal reports `insufficient data`, never a value); (7) *action class* (`page`, `ticket`, `report-only`, `log-only`) and *owner*; (8) *runbook link*; (9) *evidence of testing* (recall, detection delay, and false-alarm rate against planted incidents, with intervals, and the evidence label). A signal without a complete card is a defect.**
- **The reference-window convention (defined once).** **Every drift or quality comparison names its reference: the *training snapshot* (a versioned dataset hash, `../03-…`/`../05-…`), a *recent baseline* (a rolling or seasonal window — same weekday over the previous `k` weeks), or a *stated absolute rule* (a contract). The reference is versioned, hashed, and changes only by a recorded decision (for example after a retrain); a drift number without its reference is a defect.**
- **The label-delay convention (defined once).** **Every performance number or estimate states: the *prediction cohort* it covers (prediction-time window), the *label maturity cutoff* (the minimum age a prediction must have to be included), the *coverage* (fraction of the cohort with labels at computation time), the *delay distribution used or assumed* (and whether it depends on the outcome), the *estimator* (matured-cohort, inverse-probability-weighted, calibration-based, or sampled-label) and its *assumptions*, and an *interval*. A performance number without a maturity statement is a defect. Label-free estimates are hypotheses to be validated against matured labels, and their historical estimation error is reported.**
- **The alert-budget convention (defined once).** **Each alert class has a *false-alert budget* (expected false alerts per owner per week, a stated `[ASSUMPTION]`), a *detection-delay target*, and a measured *alert precision* (the fraction of fired alerts that were real incidents). Thresholds are chosen to meet the budget — accounting for the number of signals, slices, and windows tested (multiplicity) — and the budget is checked against replay of clean traces and planted incidents.**
- **The telemetry-privacy convention (defined once).** **Telemetry records an *allow-list* of named fields (`../02-…` Unit 6), pseudonymous identifiers, hashes or references instead of raw inputs by default, and a stated retention; raw feature values are logged only for a sampled, justified subset under the governance of `../14-…/03-…`; a prediction log is personal data when it is about people. Sampling is explicit, unbiased where estimates are made from it, and its weights are recorded.**
- **Correctness policy.** Every worked example and key is verified **two independent ways**: (1) a hand/explicit derivation in the text, and (2) an independent computation or check (exact `Fraction`/enumeration where possible; SciPy or a spec-literal brute-force reference; a closed form checked by simulation; an optional tool as a differential oracle where installed; never importing the function under test). Measurements and simulations carry **`n`, seeds, replicates, machine description, and an interval or spread; one run is an anecdote**.
- **The Production-Readiness Card (PRC), the units convention, the test-level vocabulary, the two-clock and scheduling-time conventions, the run-record, model-package, registry, determinism-level, resource-budget-card, checkpoint, container-spec, change-axes, release-vocabulary, rollback-readiness, gate-evidence, service-contract, model-version-consistency, load-test-validity, optimisation-claim, parity-level, derived-artifact, cloud-readiness-card, destructive-action, and artifact-commit conventions** are those of the Stage 5D overview and `../01-…`–`../11-…` (link; restate the twelve PRC item names once: (1) decision, consumers, serving mode; (2) data contract and quality gates; (3) point-in-time correctness and training-serving parity; (4) reproducible build; (5) tracked runs, registry, lineage; (6) tests at four levels; (7) release gate and rehearsed rollback; (8) serving contract and budget; (9) monitoring and runbook; (10) retraining policy; (11) security, privacy, retention, model card; (12) ADR and failure-mode review). The PRC is a **course convention (`JUDGEMENT`)**, not an industry standard. The **ADR** template (context, options, decision, consequences, status) is used in every unit.
- **Statistical-validity convention.** **Every statistical monitor states: the null hypothesis or the drift definition; the test statistic or divergence; the sampling distribution or simulation used for its threshold; the effect size of practical interest (a statistically significant but practically negligible shift is *not* an incident); the multiplicity correction across features, slices, and windows; the independence assumptions and how overlapping windows break them; `n`, seeds, and intervals for every rate (Wilson). Large samples make tiny shifts "significant": thresholds are set on effect size with a confidence bound, not on p-values alone.**
- **Numerical-assertion convention.** Every floating-point comparison states its tolerance, its semantics, and why; no `==` on floats unless bit-exactness is guaranteed and tested; **zero-count bins in divergences are handled by an explicit, stated smoothing rule (and the effect of the rule is shown); logarithm base is stated; histogram bin edges are fixed from the reference and versioned**; probabilities and rates state their denominators; every interval states its method and `B`/`n`; percentile definition and estimator stated; units always stated.
- **Original-content policy.** All problems, data, incidents, dashboards, runbooks, and reports are original or synthetic. Named results, books, standards, and tools are referred to **by name and own-words statement only**, never by reproducing documentation, tutorials, or example code.
- **Randomness and time policy.** Every randomized component takes an explicit `Generator`/seed derived from a recorded root seed with named spawn keys (**traffic, feature values, labels, label delays, incident onsets, noise, bootstrap, permutation, and shuffles use distinct named keys**); tools never read the system clock inside logic (inject a clock); window, alert, and delay logic runs on a virtual clock; no test sleeps; **event time and processing time are distinct (the two-clock convention of `../03-…`) and late data has an explicit rule**; wall-clock timing appears only at the CLI edge and is reported with spread; simulated time is data.
- **Data and security policy.** All data local, human-readable (JSON/JSONL/TOML/YAML/CSV/`.py`), validated, written atomically (reuse `../03-…`); no PII, no telemetry leaving the machine, no network beyond loopback; **never deserialise a model before verification (`../05-…` Unit 3)**; telemetry follows the telemetry-privacy convention; **no secrets, tokens, hostnames, usernames, or absolute paths in any output; dashboards and reports contain aggregates and pseudonymous ids only**; query strings, labels, and log fields are allow-listed and escaped (**the HTML renderer escapes every interpolated value — a planted XSS-style string must render inert**); paths resolved inside the project root with traversal and symlink escapes rejected; planted secrets are obviously fake.
