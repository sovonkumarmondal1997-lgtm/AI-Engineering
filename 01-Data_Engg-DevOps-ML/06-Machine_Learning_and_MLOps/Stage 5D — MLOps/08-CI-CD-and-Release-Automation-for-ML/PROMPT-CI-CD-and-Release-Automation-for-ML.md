## Conventions stated once, used everywhere

- **Claims policy.** Every claim about learning efficacy, study method, hiring, role requirements, CI service/strategy/tool popularity, "industry standard" status, tool maintenance, delivery-performance benchmarks, gate margins, significance levels, canary fractions, hold times, rollback triggers, or superiority is exactly one of: (a) cited from a T1/T2 source tagged `[VERIFY]` with its limits; (b) practitioner opinion tagged `[JUDGEMENT]`; (c) a verifiable statement about code, a derivation, a measurement, or the repository tree; or (d) omitted. **No success rates, no outcome guarantees, no statements about what any named company does, no invented quotes or anecdotes, no rankings, no real prices, no DORA-style figures for named teams.** All durations are `[ASSUMPTION]` templates; **all rates, costs, effect sizes, and harm values in examples are `[ILLUSTRATIVE]` parameters**.
- **Correctness policy.** Every worked example and key is verified **two independent ways**: (1) a hand/explicit derivation or a read-through of the dialect's documented semantics in the text, and (2) an independent computation or check (exact `Fraction`/enumeration where possible; a spec-literal brute-force reference; a closed form checked by simulation; never importing the function under test). Measurements and simulations carry **`n`, seeds, replicates, and an interval or spread**; one simulated release is an anecdote.
- **The Production-Readiness Card (PRC), the units convention, the test-level vocabulary, the two-clock and scheduling-time conventions, the run-record, model-package, and registry conventions, the determinism-level convention, the resource-budget card, the checkpoint convention, and the container-spec convention** are those of the Stage 5D overview and `../01-…`–`../07-…` (link; restate the twelve PRC item names once: (1) decision, consumers, serving mode; (2) data contract and quality gates; (3) point-in-time correctness and training-serving parity; (4) reproducible build; (5) tracked runs, registry, lineage; (6) tests at four levels; (7) release gate and rehearsed rollback; (8) serving contract and budget; (9) monitoring and runbook; (10) retraining policy; (11) security, privacy, retention, model card; (12) ADR and failure-mode review). The PRC is a **course convention (`JUDGEMENT`)**, not an industry standard. The **ADR** template (context, options, decision, consequences, status) is used in every unit.
- **The change-axes convention (defined once; used identically everywhere; a course convention).** An ML system changes along **three axes**: **code** (source, configuration, feature definitions, pipeline definitions), **data** (new snapshots, schema or contract changes, upstream-source changes), and **model** (a new trained candidate, a new hyper-parameter or architecture, a retrain on new data). **Every pipeline run is described by a *change set* over these axes and by the *artifacts* it consumes and produces** (a commit, a data snapshot id and manifest (`../03-…`), a lock hash (`../06-…`), a trained candidate and its package hash (`../05-…`), an image digest (`../07-…`), an evidence bundle); **a pipeline's trigger set must cover all three axes — a pipeline that reacts only to code is an ML pipeline with a blind spot.**
- **The release-vocabulary convention (defined once; used identically everywhere).** A **release** exposes a **candidate** (the new model version, `../05-…`) to traffic in place of or alongside the **champion** (the current model). **Shadow**: the candidate receives a copy of live requests and its outputs are *recorded and compared but never returned to users and never allowed to write to shared production state*. **Canary**: a **fraction `f`** of **units** (users, sessions, or requests — the *assignment unit* is stated) is served by the candidate, with **guardrails** (metrics whose breach aborts) and **decision metrics** (metrics that decide promotion). **Blue-green**: two complete environments, **blue** (serving) and **green** (candidate), with an atomic switch of routing. **A ramp** is a schedule of fractions with hold times; **assignment is sticky** (a unit always gets the same arm for the same experiment) **and nested** (the units in the 5% arm are a subset of those in the 25% arm). **Promotion** moves the champion alias (`../05-…` Unit 6); **abort/rollback** returns routing and/or the alias to the previous champion.
- **The rollback-readiness convention (defined once).** **Rollback is possible iff the previous champion is (i) retained and verified loadable, (ii) *compatible with the current state of every shared contract* — the feature schema, the serving request/response schema, the configuration, and any persisted state the candidate may have written — and (iii) deployable within the rollback time budget.** **The compatibility relation is over the triple (model version, feature/contract version, serving-schema version); a release that removes a feature, renames a field, or migrates state without an N−1 window is a *one-way* change and is classified as such *before* release.** **A rollback restores *future* behaviour; it does not undo past decisions — the *affected-decision set* (predictions served by the bad version) is identified and remediated separately.**
- **The gate-evidence convention (defined once).** **A quality gate is a pure function from a *recorded evidence bundle* and a *gate specification* to a verdict (`pass`, `fail`, `waived`, `insufficient_evidence`) with the full list of checks, their results, and the evidence hashes read; gates never retrain, re-evaluate on unrecorded data, or read evidence whose subject hash differs from the candidate being gated (`../05-…` Unit 6).** **Every gate carries its decision problem (what a wrong pass and a wrong block cost), its null hypothesis, its derived false-block and false-pass behaviour, and the data it is evaluated on — a frozen *gate set* disjoint from any data used to train or select the candidate.**
- **Numerical-assertion convention.** Every floating-point comparison states its tolerance, its semantics, and why; no `==` on floats unless bit-exactness is guaranteed and tested; **probabilities and rates state their denominators; every interval states its method (Wilson, Clopper–Pearson, percentile bootstrap, normal approximation with its conditions) and `B` or `n`; "significant" is never used without the test, the level, and the multiplicity handling**; percentile definition and estimator stated; time in seconds with the clock stated.
- **Original-content policy.** All problems, data, pipelines, traffic, regressions, and incidents are original or synthetic. Named results, books, specifications, and tools are referred to **by name and own-words statement only**, never by reproducing documentation, tutorials, or example workflows.
- **Randomness and time policy.** Every randomized component takes an explicit `Generator`/seed derived from a recorded root seed with named spawn keys (**traffic arrivals, outcomes, assignment salts, regressions, defect injection, noise, bootstrap, and shuffles use distinct named keys**); tools never read the system clock inside logic (inject a clock); **release, canary-hold, and rollback logic runs on a virtual clock**; no test sleeps; wall-clock timing appears only at the CLI edge and is reported with spread; simulated time is data.
- **Data and security policy.** All data local, human-readable (JSON/JSONL/TOML/YAML/CSV/`.py`), validated, written atomically (reuse `../03-…`); no PII, no telemetry, no network at run time; **hosted-CI configuration files and pipeline specs are parsed with `safe_load`/strict loaders and never executed by the learner's tools**; **pipeline security hygiene is a first-class topic: least-privilege permissions, short-lived credentials over stored secrets, secrets never echoed or written to logs/artifacts/caches, third-party actions/plugins pinned to immutable references, no exposure of secrets or privileged tokens to code from untrusted contributors (`CITED [VERIFY]` against the service's own security documentation), protected branches and required checks, and no use of the unsafe-loader or shell-interpolation of untrusted input — each verified statically on the course's dialect `[VERSION-SENSITIVE]`**; **evidence bundles and gate reports contain identifiers and hashes, not rows or personal data**; model files are loaded only after the verification of `../05-…` Unit 3; routing assignment uses a **keyed hash of a pseudonymous unit id, never raw identifiers**; paths resolved inside the project root with traversal and symlink escapes rejected; **no secrets, hostnames, usernames, tokens, or absolute paths in any output**; planted secrets are obviously fake.
- **Integrity and ethics policy.** Work is the learner's own; AI assistance is allowed for explanation and review, **must be disclosed in the evidence log**, and AI-generated pipelines, gate thresholds, canary schedules, and rollback plans are **untrusted hypotheses verified against a check** (a generated pipeline is linted and structurally compared; a generated gate is run against planted regressions and clean controls; a generated rollback plan is rehearsed). Honest self-representation (**never edit gate evidence, thresholds, or release logs after the fact; never reuse a holdout until it passes; never report a canary after peeking as if it were a fixed-horizon test**); accessibility (text alternatives for diagrams — a table or edge list accompanies every pipeline, ramp, or compatibility diagram); anxiety about release engineering acknowledged as a real experience (awareness only, `[JUDGEMENT]`, no clinical claims); **responsible-use note: a released model makes or supports decisions about people; gates, staged exposure, and rollback exist to limit harm; affected-decision remediation is part of release recovery; segments with small samples need extra care; no legal claims**.
- **Result status vocabulary:** `PROVED`, `CITED`, `EVIDENCE ONLY`, `HEURISTIC`, `JUDGEMENT` (markers: `[ASSUMPTION]`, `[ILLUSTRATIVE]`, `[VERSION-SENSITIVE]`, `[VERIFY]`). **Exhaustive or seeded testing, simulation, a green pipeline, a passing gate, and a successful canary never upgrade a status to `PROVED`.**
- **Stage gate convention (inherits the repository's):** ≥ 80% proceed; 60–79% remediate named lessons and retake; < 60% repeat prerequisites.
