## Conventions stated once, used everywhere

- **Claims policy.** Every claim about learning efficacy, study method, hiring, role requirements, pattern/tool popularity, "industry standard" or "best practice" status, tool maintenance, product performance or cost, or superiority is exactly one of: (a) cited from a T1/T2 source tagged `[VERIFY]` with its limits; (b) practitioner opinion tagged `[JUDGEMENT]`; (c) a verifiable statement about code, a derivation, a measurement, a simulation, or the repository tree; or (d) omitted. **No success rates, no outcome guarantees, no statements about how any named company architects or operates systems, no invented quotes or anecdotes, no rankings, no product performance figures.** All durations are `[ASSUMPTION]` templates; **all rates, sizes, costs, and capacities in examples are `[ILLUSTRATIVE]` parameters or planted values labelled as such**.
- **The evidence-label convention (reused from `../09-…`, restated once).** Every statement about a system's behaviour carries exactly one label: **`MEASURED`** (observed on this machine, for this workload and configuration, with repetitions and an interval), **`SIMULATED`** (a seeded model or planted-scenario replay with stated assumptions; validated against `MEASURED` data where any exists), **`DOCUMENTED`** (stated in named official documentation for a stated version and date; not independently verified), or **`NOT ASSESSED`**. **A freshness, latency, cost, availability, or quality figure without a label is a defect. Architecture-model results are `SIMULATED` or analytic with stated assumptions; they are never "the performance of the architecture" in the real world.**
- **The architecture-model convention (AMC; defined once; extends the architecture-spec language of `../11-…` Unit 1; a course convention).** **An architecture is represented as a *checkable model*: *components* (typed: source, feature pipeline, store, model service, router, queue, stream operator, review stage, monitor, …) with *roles*; *flows* between them (data, control, and decision flows) annotated with *rate, volume, latency distribution, freshness contribution*, and *delivery semantics*; *state and consistency* (what is stored where, how it is versioned, what can be stale); *failure behaviour* (each component's availability, failure modes, and fallback rung per `../14-…` Unit 2); *cost parameters* (per-unit costs as `Decimal` with source or `[ILLUSTRATIVE]`); and *quality-attribute scenarios* (below). **Every parameter carries an evidence label, a value or interval, and a source; the model refuses an unlabelled parameter.** Analytic evaluators and a discrete-event composition simulator compute the quality attributes from the model; **the evaluators are validated against each other and against exact enumeration on small instances.****
- **The quality-attribute-scenario convention (QAS; defined once; a course convention after the architecture-evaluation literature, `CITED [VERIFY]`).** **A quality requirement is a *scenario* with six parts: *source* (who or what generates the stimulus), *stimulus*, *environment* (normal, peak, degraded), *artifact* (what is stressed), *response* (what the system does), and *response measure* (a number with a unit and a percentile or probability). A scenario is *testable* when an evaluator in the architecture model, a simulation, or a measurement can produce the response measure; a requirement stated as an adjective ("scalable", "reliable") with no scenario is a defect. Scenarios are prioritised in a *utility tree* by ordinal *importance* and *difficulty* (`JUDGEMENT`).**
- **The pattern-card convention (defined once; a course convention).** **Every architecture pattern is specified by a *pattern card*: *context and problem*; *forces*; *solution* (the model fragment); *consequences* for each quality attribute **stated as formulas or parameter regimes, not adjectives**; *prerequisites*; *known failure modes*; *fitness functions* that detect those failure modes; *when not to use* (a pattern card without a when-not is a defect); and *evidence* (which evaluator and which simulation substantiate the consequences). Patterns are compared only by *regimes and break-evens*, never ranked.**
- **The trade-off-evidence convention (TEC; defined once; a course convention).** **A trade-off claim ("batch is cheaper", "streaming is fresher") states: the *two or more attributes* in tension; the *parameter regime* in which each side wins; the *break-even value* of the deciding parameter(s) with its *derivation*; the *sensitivity* of the decision to the parameters (which uncertain parameter, within its interval, flips the decision); the *evidence label*; and the *monitoring plan* for the parameter (the *assumption monitor*: a monitoring-signal card of `../12-…` that fires when the measured parameter approaches the break-even). The phrase "it depends" is not an answer; "it depends on request rate `λ`, with break-even `λ*`, currently `x`, interval `[a, b]`" is.**
- **The fitness-function convention (defined once; after the evolutionary-architecture literature, `CITED [VERIFY]`).** **A *fitness function* is an automated check that an architectural property still holds — a latency budget evaluated on the architecture model or a measured load test, a freshness bound, a cost cap, an availability target, a dependency rule (for example *no online path depends on a batch-only store*), a data-residency rule, a parity test, a schema-compatibility test. Fitness functions run in CI against the architecture model and the deployed configuration; each has a *measured detection rate against planted regressions* and a *false-alarm rate*.**
- **The routing convention (defined once; extends `../08-…` Unit 3 and `../13-…` Unit 5).** **Every router specifies: the *assignment unit* (request, user, session, entity, tenant); *stickiness* (a deterministic salted hash so the same unit gets the same arm while the configuration is fixed, and *nested exposure* so raising an arm's share only adds units); the *policy* (weighted split, segment rule, cascade, ensemble, bandit); *exposure fractions* and their *cost* (Unit 4); *logged propensities* for every decision (the probability the policy assigned the realised arm) so off-policy evaluation is possible (`../13-…` Unit 5); *interference controls* (arm-keyed caches, resource isolation); *disclosure* (the response states the arm and model version — `../09-…` Unit 4); and *the evaluation unit* matching the assignment unit.**
- **The review-capacity convention (defined once; extends `../13-…` Unit 5 and `../14-…` Units 2, 5).** **A human-review stage is specified as a *service system*: *routing rule* (what is sent, with the expected arrival rate and its uncertainty), *capacity* (reviewers × throughput, with schedules), *deadline* (the decision window), *default action on expiry* (a rung of the degradation ladder with its safety check — never an unexamined "approve"), *priority policy*, *reviewer-accuracy evidence* (gold items), *score-visibility policy* with a measured anchoring effect, *override and decision logging* (audit-trail events), *feedback to training* with routing propensities, and *group-wise review burden* (the fairness-evidence convention). A review stage whose capacity has not been compared with its routed load is a defect.**
- **Correctness policy.** Every worked example and key is verified **two independent ways**: (1) a hand/explicit derivation in the text, and (2) an independent computation or check (exact `Fraction`/enumeration where possible; SciPy or a spec-literal brute-force reference; a closed form checked by simulation; never importing the function under test). Measurements and simulations carry **`n`, seeds, replicates, machine description, and an interval or spread; one run is an anecdote**.
- **The Production-Readiness Card (PRC), the units convention, the test-level vocabulary, the two-clock and scheduling-time conventions, the run-record, model-package, registry, determinism-level, resource-budget-card, checkpoint, container-spec, change-axes, release-vocabulary, rollback-readiness, gate-evidence, service-contract, model-version-consistency, load-test-validity, optimisation-claim, parity-level, derived-artifact, cloud-readiness-card, destructive-action, artifact-commit, monitoring-signal-card, reference-window, label-delay, alert-budget, telemetry-privacy, statistical-validity, retraining-policy-card, autonomy-ladder, training-data-cut, champion–challenger-evidence, feedback-loop, holdout-reuse-ledger, SLO-card, degradation-ladder, data-handling, accountability-evidence, fairness-evidence, incident, and risk-and-threat conventions** are those of the Stage 5D overview and `../01-…`–`../14-…` (link; restate the twelve PRC item names once: (1) decision, consumers, serving mode; (2) data contract and quality gates; (3) point-in-time correctness and training-serving parity; (4) reproducible build; (5) tracked runs, registry, lineage; (6) tests at four levels; (7) release gate and rehearsed rollback; (8) serving contract and budget; (9) monitoring and runbook; (10) retraining policy; (11) security, privacy, retention, model card; (12) ADR and failure-mode review). The PRC is a **course convention (`JUDGEMENT`)**, not an industry standard. The **ADR** template (context, options, decision, consequences, status) is used in every unit, **extended here with *assumptions*, *break-even parameters*, and a measurable *revisit trigger* (Unit 5)**.
- **Numerical-assertion convention.** Every floating-point comparison states its tolerance, its semantics, and why; no `==` on floats unless bit-exactness is guaranteed and tested; **money is `Decimal` or integer minor units with a labelled source or `[ILLUSTRATIVE]`**; probabilities and rates state their denominators; every interval states its method and `B`/`n`; percentile definition and estimator stated; time units always stated with the clock named (event, processing, label-available, wall).
- **Original-content policy.** All problems, data, architectures, case studies, and incidents are original or synthetic. Named results, books, and patterns are referred to **by name and own-words statement only**, never by reproducing their text; **no real company's architecture is described or implied**.
- **Randomness and time policy.** Every randomized component takes an explicit `Generator`/seed derived from a recorded root seed with named spawn keys (**arrivals, entity popularity, event lateness, redelivery, reviewer behaviour, routing assignment, bandit draws, parameter uncertainty, bootstrap, and shuffles use distinct named keys**); tools never read the system clock inside logic (inject a clock); stream, queue, routing, and refresh logic runs on a virtual clock; no test sleeps; **event time and processing time are distinct (`../03-…`) and every windowed result states which clock defines it**; wall-clock timing appears only at the CLI edge; simulated time is data.
- **Data and security policy.** All data local, human-readable (JSON/JSONL/TOML/YAML/CSV/`.py`), validated, written atomically (reuse `../03-…`); no PII, no telemetry, no network beyond loopback; **never deserialise a model before verification (`../05-…` Unit 3)**; architectures that move personal data state the data-handling-convention fields (`../14-…` Unit 3) and residency (`../11-…` Unit 1); review-stage designs follow the telemetry-privacy and fairness-evidence conventions; **routers and caches never serve one arm's predictions to another arm's units; no secrets, tokens, hostnames, usernames, or absolute paths in any output**; manifests, scenarios, and decision records are parsed with strict loaders (`safe_load` for YAML) and never executed; paths resolved inside the project root with traversal and symlink escapes rejected.

Honest self-representation (**never present a case study's numbers as transferable; never present a modelled result as a measurement; never rank patterns or products; never claim an architecture is "scalable" or "reliable" without a scenario and a response measure**); accessibility (text alternatives for diagrams — a table or edge list accompanies every architecture, flow, and state-machine diagram); anxiety about architecture as abstraction acknowledged as a real experience (awareness only, `[JUDGEMENT]`, no clinical claims); **responsible-use note: architecture decisions allocate harm and cost — to the people whose decisions are automated or delayed, to reviewers whose workload is set by a threshold, to groups routed differently; the review-capacity, routing-disclosure, degradation, and fairness hooks exist to make those allocations visible and defensible; no legal claims**.
