2. AI self-audit is not independent. Run every lab with your installed tool versions and close every `[VERIFY]` item against current official docs. All tokens, keys and outputs in the syllabus will be representative fakes, not captured from real runs.
3. **Do not let any real secret near this course.** The prompt forces fake, lab-generated credentials and clearly non-matching placeholder formats, so your repository's secret scanners do not fire. Do not reuse a real password, key or token in any lab. If a real one slips in, rotate it first and purge Git history second.
4. Highest fabrication risk, check first:
   - Vault paths and policy syntax, especially the KV v2 `data/` path layout.
   - Kubernetes and JWT auth role fields.
   - Database engine fields and `rotate-root`.
   - Raft snapshot commands.
   - ESO CRD API versions and fields.
   - Secrets Store CSI rotation feature status.
   - SOPS and kubeseal flags.
   - kind config for encryption at rest and for the OIDC issuer (kubeadm patches).
   - Kubernetes KMS v1 versus v2 status.
   - JWT claim names.
   - gitleaks config keys.
   - `git filter-repo` options.
5. Scope decisions I made, which you can change:
   - The tooling map lists everything here except Kubernetes Secrets and RBAC as Awareness, but this folder has dedicated modules for them. The prompt teaches Vault or OpenBao, ESO, SOPS, Sealed Secrets, the CSI driver, encryption at rest, a local workload-identity simulation and gitleaks at working depth.
   - Exactly one Vault-compatible server is hands-on. Please pick Vault or OpenBao, or let the syllabus pick. The prompt tells the LLM not to assert licensing or governance facts, so read both projects' current licences yourself.
   - Workload identity is simulated locally, with the kind API server as the OIDC issuer, a small verifier service and Vault JWT auth. The tooling map marks it "not feasible free". IRSA, GCP Workload Identity Federation and Azure Workload Identity are Awareness only, with illustrative manifests labelled "not run in labs". LocalStack STS and SPIRE are optional, with explicit fidelity statements.
   - Unit 5 goes deeper on SOPS and Sealed Secrets than M08 Unit 5 did. The audit passes check that the two do not contradict each other. If you change M08's secret tool, adjust this unit.
6. Several labs are high-risk on purpose, though only on throwaway clusters and repos the lab creates. They are the encryption-key loss, Vault root-credential rotation, history rewrite and forced mass lease revocation. Each is labelled and has a recovery path.
7. The leak-response game day uses a credential that is actually valid in your lab (a Vault dynamic DB user or a stub token), not a real cloud key. Never test discovered third-party credentials. The prompt bans credential-testing and brute-force tooling.
8. Ordering is taught as a rule: revoke first, purge history later. Purging history is shown not to be remediation.
