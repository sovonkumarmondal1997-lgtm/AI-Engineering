# 9. Phase B — Silver Layer in Polars

Use Polars **LazyFrame** APIs.

1. Read raw/landing data.
2. Enforce explicit dtypes.
3. Normalize timestamps.
4. Validate business constraints.
5. Separate invalid rows into a quarantine dataset.
6. Deduplicate by `trip_id`.
7. Derive useful analytical columns where appropriate.
8. Use lazy execution.
9. Use streaming execution where supported.
10. Write Silver Parquet output.

Include a clearly documented explanation of:

- why lazy execution is used
- which operations can be streamed
- where state-heavy operations exist
- how memory is managed
- what happens when the dataset is larger than RAM

Do not use Python row-wise UDFs unless there is no reasonable expression-based alternative.

# 10. Phase C — Gold Layer in DuckDB

Use DuckDB as the SQL-first analytical layer.
The Gold layer must include all of the following:

## Daily zone metrics

Produce daily metrics such as:

```
trip_date
pickup_zone_id
trip_count
total_revenue
average_fare
average_distance
```

## Monthly zone metrics

Produce equivalent monthly metrics.

## Top-N routes per borough

Use `QUALIFY` to produce the top-N routes within each borough.
The SQL must clearly demonstrate a window function / ranking pattern.

## Fare rules

Use a **time-aware `ASOF JOIN`** to match trips to the applicable fare rule based on effective date/time.
Apply the matched fare rule to produce a derived metric such as an adjusted fare.
Do not fake the `ASOF JOIN`; it must be a real time-based join over the effective rule history.

## Output

Write Gold results back to MinIO as Parquet.
Use:

```
COPY ... PARTITION_BY (...)
```

or the current equivalent supported by the installed DuckDB version.
Keep the output layout analytically useful.

A benchmark result is evidence for this workload, this data, this hardware, and this implementation.
